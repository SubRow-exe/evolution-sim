## 1. 目的

V1.8ではlightとchemicalを「同じEnergyの別field」として扱うだけでなく、**一次Energy源として異なる生態的性質**を持たせる。

狙う構造:

```text
light
- 空間的に広い
- 1地点・1tickの利用可能fluxは比較的薄い
- stockではなくrenewable flow
- 昼夜で周期的に0になる
- 受光面積と光強度に依存
- 高い活動コストを払う戦略は自然に不利になり得る

chemical
- vent近傍へ局在
- 局所stockは高くなり得る
- 見つければ高い瞬間Energy獲得速度を持てる
- 個体が使うとstockが減る
- 同じstockを個体間で奪い合う
- sourceは再供給するが、局所stockは一時的に枯渇できる
```

**「光型を弱くする」「chemical型を強くする」という適応度補正は入れない。**

環境場・資源の時間構造・濃度依存吸収・既存コストから結果を生じさせる。

# 3. V1.8で変更するもの

## 3.1 lightに昼夜cycleを導入

現在の `World.light` は静的空間fieldで、毎tick常に同じfluxが使える。

V1.8でも `World.light` 自体は**昼のpeak/base空間field**として保持する。

実際にそのtickで利用できるlightは:

```text
F_light(ix, iy, tick) = World.light[ix, iy] * daylight_factor(tick)
```

とする。

### cycle形状

Config:

```python
light_cycle_enabled: bool = False       # Exp13選定前はV1.7互換のためFalse
light_cycle_period_ticks: int = 200
light_day_fraction: float = 0.5
```

V1.8ではcycle shapeは設定項目を増やさず**half-sine固定**。

```text
phase = (tick mod period) / period

if phase < day_fraction:
    u = phase / day_fraction
    daylight_factor = sin(pi * u)
else:
    daylight_factor = 0
```

性質:
- run開始は夜明け (`factor=0`)
- 日中中央でpeak (`factor=1`)
- 日没で0
- 夜間は厳密に0
- 不連続なON/OFF矩形波を避ける
- period=200 / day_fraction=0.5なら100 tick daylight + 100 tick night

`light_cycle_enabled=False` では:

```text
daylight_factor = 1.0
```

とし、V1.7と完全一致すること。

### period=200の位置づけ

tickを現実の秒へ対応させない。

200 tickは:
- 現行の移動・Energy storage・世代時間に対してcycleを観察可能
- 10k runで50 cycleを含む
- nightを単なる1〜2 tickのnoiseにしない

ためのシミュレーション内部timescaleとして採用する。

Exp13ではperiod自体を結果へ合わせてチューニングしない。将来、日長・季節を扱う際に別実験で変更する。

## 3.2 Energy吸収を局所濃度/強度依存にする

V1.4以降の共通原則:

```text
A_eff = matter^(2/3)
```

および同一cell内の需要比例公平配分は維持する。

V1.8では、個体の最大要求量へ局所field強度の飽和responseを追加する。

共通helper:

```text
H(x, K) = x / (x + K)
```

- x=0 -> 0
- x=K -> 0.5
- x->infinity -> 1

**V1.5の知覚responseとは目的が異なるため、知覚用 `*_stimulus_half` を流用しない。**

### Config

```python
primary_energy_density_response: bool = False
light_uptake_half: float = 0.6
chemical_uptake_half: float = 6.15
```

選定前のdefaultはfeature OFFとしてV1.7完全回帰を守る。

Exp13ではfeature ONで実験する。

`light_uptake_half` / `chemical_uptake_half` は正値必須。

初期候補値の根拠:
- 現行標準light peak `1.2` の1/2 -> `0.6`
- 現行標準vent生物不在stock約`12.3`の1/2 -> `6.15`

これは絶対値の最終校正ではなく、各resourceの既存標準スケールに対する半飽和点を置くもの。

---

## 3.3 新しいlight吸収式

そのtickのcell light flux:

```text
I = base_light[ix,iy] * daylight_factor
```

個体iの要求:

```text
raw_i = light_uptake_coef
        * light_absorption_i
        * A_eff_i
        * phi_i
        * H(I, light_uptake_half)
```

Energy容量の残りでcapした後、cell供給 `I` に対し従来どおり需要比例配分する。

したがって:

```text
sum(light_gain_i) <= I
```

を常に満たす。

lightはstockとして減算しない。同一tickの供給を取り合うが、次tickには新しい外部fluxとして再供給される。

夜間 `I=0` ならlight gainは厳密に0。

---

## 3.4 新しいchemical吸収式

cell chemical stock:

```text
C = world.chemical[ix,iy]
```

個体iの要求:

```text
raw_i = chem_uptake
        * chemical_absorption_i
        * A_eff_i
        * phi_i
        * H(C, chemical_uptake_half)
```

Energy容量残りでcapした後、stock `C` に対し需要比例配分する。

```text
sum(chemical_gain_i) <= C
world.chemical[cell] -= sum(chemical_gain_i)
```

現在の地質source / loss:

```text
loss = chem_loss_frac * stock
stock = stock - loss + chem_source_flux
```

は維持する。

### 「枯渇」の意味

V1.8で枯渇するのは**局所stock**である。

地質sourceそのものには有限寿命をまだ導入しない。

したがって:
- 大量消費 -> stock低下
- 低stock -> 1個体あたり吸収速度低下
- 個体が多い -> 奪い合い
- 消費が減る -> sourceにより再蓄積

となる。

vent自体の誕生・停止・有限寿命は将来の環境変動versionへ送る。

---

## 3.5 chemicalの「高い瞬間収益」は `chem_uptake` で校正

chemicalへ固定Energy bonusは追加しない。

既存:

```text
chem_uptake = 0.5
```

は最大処理速度係数としてそのまま意味を持つ。

Exp13 Phase Aでは:

```text
chem_uptake = 1.0, 2.0, 4.0
```

を候補とし、**条件を満たす最小値**を恒久値候補とする。

目標は、vent上で高stockに出会ったchemical specialistがlight specialistの日中取得より明瞭に高い瞬間収益を得られる一方、stock枯渇後はその高収益を無制限に維持できない状態。

# 4. 生理コスト

## 4.1 route-specific penaltyは追加しない

現行:

```text
organ_upkeep * matter * (
 light_absorption + chemical_absorption + nutrient_absorption
 + predation_efficiency + corpse_digestion
)
```

により、高いlight/chemical能力はいずれも維持費を持つ。

V1.8では:
- `light_absorption`だけ特別に高い維持費を課さない
- chloroplast maintenanceという専用項を追加しない
- chemicalにも人工的bonus/penaltyを足さない

理由:
- 現在の世界は原核生物/LUCA-inspired段階
- 細菌のphototrophyは葉緑体を必要としない
- photosynthetic apparatusもchemical metabolism machineryも維持費を持つという共通表現が既にある

光の低い平均収益＋夜＋移動費によって、高活動戦略が自然に不利になるかを見る。

## 4.2 「植物は動かない」を実装しない

light userのmovement_powerを直接下げない。

移動可能性は全個体で維持する。

光で得られるEnergyが薄ければ、既存のmovement cost:

```text
move_cost * matter * v^2 / movement_efficiency
```

との収支から、低活動が自然選択される可能性を残す。

# 5. 行動・知覚との接続

V1.6 temporal sensingは維持する。

ただしlight知覚は静的 `World.light` ではなく**そのtickのeffective light**を見る。

```text
R_light = response(effective_light, light_stimulus_half)
```

chemicalは現在stockを従来どおり見る。

したがって:
- sunrise -> light刺激増加
- sunset -> light刺激低下
- night -> light刺激0
- chemicalが存在すればnightもchemical刺激は残る

となる。

`light_stimulus_half=1.2` / `chemical_stimulus_half=12.3` はV1.5/V1.6知覚校正値であり、V1.8の吸収halfとは独立に維持する。

# 6. Energy台帳・Recorder必須修正

現在 `light_supply_cum` は:

```text
static_light_supply_per_tick * tick
```

で計算しているため、昼夜導入後は誤る。

V1.8ではSimulationに実供給累積を持たせる。

推奨:

```python
self.light_supply_cum = 0.0
```

各tick:

```text
current_light_supply = sum(World.light) * daylight_factor
light_supply_cum += current_light_supply
```

Recorder `light_supply_cum` はこの実測累積値を書く。

追加観測:

```text
light_cycle_factor
light_supply_rate
```

を `stats.csv` に追加する。

これらは観測専用で進化へ戻さない。

`World.light` のstatic environment snapshotは**peak/base light field**として保存し、昼夜で毎snapshot複製しない。

`mean_local_light` は既存互換のためbase/peak habitat指標として残す。実効値は:

```text
mean_local_light * light_cycle_factor
```

で再構成可能とする。

# 7. high-Q mask等の観測定義

`hi_q_mask` は進化へ使わない観測専用なので、昼夜で毎tick変動させない。

V1.8でも:

を使ってstatic maskを作る。

昼夜実効値を使う指標が必要なら別列として出し、既存 `hi_q_mask` の意味を黙って変更しない。

# 11. 科学的設計原則

V1.8で期待するのは「phototrophが弱くなること」そのものではない。

確認したいのは:

> **同じEnergy単位を使いながら、sourceの物理的性質だけで異なる生活史trade-offが生まれるか**

である。

望ましい概念図:

```text
light user
renewable / broad / low-average flux / night zero
        +
area dependence / organ upkeep / movement cost
        -> 安定だが節約型になりやすい

chemical user
localized / stock / high burst / depletion / competition
        +
search & movement cost
        -> 不安定だが資源発見時に高収益
```

この構造が成立したかをExp13で検証する。
