# オンライン実行・開発環境

更新: 2026-08-29

ローカルPCを必須にせず、GitHub中心で開発と本番計算を完結させるための構成。

```
GitHub (Public)
  ├─ Codespaces : 開発 (VS Code / テスト / 軽い確認)
  ├─ Actions    : 本番計算 (run単位でmatrix並列)
  └─ Issues/docs: 方針・実験管理・要約・チェックサム

外部ストレージ (Google Drive / OneDrive)
  └─ 生データ (events.csv 等の大容量ファイル)

ローカルPC
  └─ GUIビューアによる観察 / 予備
```

---

## 1. 開発環境: Codespaces

`.devcontainer/devcontainer.json` があるため、Codespaceを開けば自動で環境が整う。

| 項目 | 内容 |
|---|---|
| ベース | `mcr.microsoft.com/devcontainers/python:1-3.12-bookworm` |
| 依存 | `pip install --user uv && uv sync --frozen` (lockfileどおり) |
| 環境変数 | `SDL_VIDEODRIVER=dummy` / `MPLBACKEND=Agg` |

画面が無くても pygame の import と matplotlib は動作する。
**GUIビューア (`main.py` の `--headless` なし) は動かない。** 観察はローカルPCで行う。

### 無料枠に注意

Codespaces の無料枠は **Actions とは別枠** で、Public 化しても増えない。
個人アカウントは月 **120コア時間**（2コアマシンで60時間）+ ストレージ15GB。

**本番シミュレーションはCodespacesで回さない。** 開発用途に温存する。

## 2. 本番計算: Actions

Public リポジトリなので標準ランナーの Actions 分は無料。

| ワークフロー | 用途 | 起動 |
|---|---|---|
| `ci.yml` | テスト・結果不変性検証 | push / PR で自動 |
| `benchmark.yml` | 計算性能の測定 | 手動 |
| `exp04.yml` | Exp04 本番 (200 run) | 手動 |
| `drive_check.yml` | Google Drive 転送経路の疎通確認 | 手動 |

### 分散の方針

1ランナーは**物理1コア**（実測: Xeon 8370C、2スレッドだが並列効果なし）。
1ランナー内で複数workerを動かしても速くならないため、
**「1 run = 1 Actions job」で横方向に分散**する。`max-parallel: 20`。

### Exp04 の実行

```bash
gh workflow run exp04.yml \
  -f conditions=baseline,body_size,reproduction_investment,mutation_rate,light_absorption \
  -f seeds=1-40 -f ticks=40000
```

200 run、実時間 約6時間。**Exp04 の正本は `docs/Exp04_実行手順.md`**
（本文が Actions 前提。Windows ローカルは同書の付録A）。

本番前に転送経路だけを確認する場合:

```bash
gh workflow run drive_check.yml
```

数KBのテストファイルをアップロード→再取得し、SHA256の一致まで確認して削除する。

## 3. 数値実行環境の統一

`math.sin/cos/atan2/hypot` と `pow` はOS側の数学ライブラリ実装に依存するため、
**同じseedでもWindowsとLinuxで結果が一致しない。**

そのため今後の正式実験は **Linux / GitHub Actions に統一する。**

- Exp04 から移行する
- Exp04 では baseline も Actions 上で取り直す（200 run）
- **Windows版 Exp03 (13/20) は削除せず過去の参考実験として保存する。**
  Exp04 の正式比較には使わない

各runの `meta.json` に環境が自動記録される。`tools/check_env.py` で混在を検出できる。

## 4. 実験データの保存

生データは巨大なため GitHub には置かない。役割を分ける。

| 保存先 | 内容 |
|---|---|
| **GitHub** | コード / Config / meta.json / NOTES.md / 集計結果 / グラフ / 再現コマンド / **SHA256チェックサム** / 保存先の識別情報 |
| **外部ストレージ** | `events.csv` / `stats.csv` / `runs/` 以下の生データ / 実験フォルダのアーカイブ |

### 流れ

```
Actions で実行 → runs/ に生データ
  → 健全性チェック (check_env)
  → 解析 (analyze_transitions)
  → 条件ごとに tar.gz へ圧縮
  → SHA256 を含むマニフェスト生成 (tools/make_manifest.py)
  → 外部ストレージへ転送 (rclone)
  → 要約・解析結果・チェックサムを GitHub へ
```

`experiments/<実験名>/<条件>/` に以下が残る。

- `MANIFEST.md` — run一覧、生データ容量、**保存先パス**、アーカイブのSHA256
- `manifest.json` — 全ファイルのSHA256（機械可読）

これにより「GitHubを見れば内容と結論が分かり、必要なら外部ストレージから
完全な生データを取得して完全性を検証できる」状態になる。

## 5. 外部ストレージ転送のセットアップ（要作業）

**未設定でも Exp04 は完走する。** その場合、生データは Actions 成果物として
90日間保持されるだけになる（`exp04-rawdata`）。

恒久保存するには以下を設定する。**認証情報はリポジトリに絶対に含めない。**

### 手順

**1. ローカルで rclone を設定し、Google Drive の認証を通す**

```bash
rclone config
```

対話に従って remote 名（例 `gdrive`）を作り、Google Drive を選んでブラウザ認証する。
完了後、設定ファイルの場所は `rclone config file` で確認できる。

**2. 設定ファイルを Base64 にする**

```bash
base64 -w0 ~/.config/rclone/rclone.conf
```

Windows の場合:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("$env:APPDATA\rclone\rclone.conf"))
```

**3. GitHub に登録する**

| 種別 | 名前 | 値 |
|---|---|---|
| **Secret** | `RCLONE_CONFIG_BASE64` | 手順2で得た文字列 |
| **Variable** | `RCLONE_REMOTE_BASE` | 例: `gdrive:evolution-sim` |

Settings → Secrets and variables → Actions から登録する。
Secret は登録後に読み出せない（GitHubが暗号化保持）。

**4. 確認**

次回の `exp04.yml` 実行で「生データを外部ストレージへ転送済み」と
Job Summary に出れば成功。

### 注意

- **Public リポジトリなので、Secret は Fork からの PR では渡らない**（GitHubの仕様）。
  意図しない漏洩を防ぐ設計になっている
- rclone の設定ファイルには**リフレッシュトークンが含まれる**。
  Base64 は暗号化ではないので、Secret 以外の場所に置かないこと
- 転送先は Drive の専用フォルダにし、他のデータと混ぜない

## 6. ローカルPCの位置づけ

必須の計算環境にはしない。

- GUIビューアによる観察（Codespacesでは動かないため）
- オンライン環境障害時の予備
- 過去のWindows実験（Exp01〜03）の保管

---

## 7. 将来の拡張

現時点で AWS 等の有料環境は導入しない。以下に該当した場合のみ再検討する。

- 同時実行数（20ジョブ）が不足する
- 大規模実験で待ち時間が問題になる
- 標準ランナーの1コア性能が問題になる

判断材料は `tools/benchmark.py` で各候補を実測して比較する
（`docs/計算特性と並列化方針.md`）。
