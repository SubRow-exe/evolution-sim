一方で、**候補値を実baselineへ当てて検算したところ、V1.11が狙っている生態的帰結が現在の数値では成立しない**ことが分かった。

# 1. 検算結果

すべて `experiments/opus5_v111_review_20260910/` で再現できる。baselineは実際に走っている `experiments/luca_proxy/run_luca_proxy.py` の `make_cfg("A")`。

## D-1 `h2_usable_energy_j_per_mol` の値が仕様書と実baselineで違う

仕様書 §7.1:

```text
既存: h2_usable_energy_j_per_mol = 3750 J/mol H2
なので十分な光があれば ... 最大約9倍（3750+30000）
```

しかし実際に走っているのは:

```text
h2_usable_energy_j_per_mol = 0.075 [mol ATP/mol H2] * 32100 [J/mol ATP] = 2407.5 J/mol
```

3750は `evosim/config.py` のdefault値で、これはExp15 Attempt 1以前の旧値である。Exp15 Attempt 2以降、Exp16・Exp17・Exp18・Exp19はすべて `luca.make_cfg()` 経由で **2407.5** を使っている。

したがって:

```text
(2407.5 + 30000) / 2407.5 = 13.5 倍
```

が正しい。仕様書の「約9倍」は**1.5倍過小評価**している。§7.1の記述を訂正すること。

これは単なる数字の誤りではない。仕様書は「9倍」を根拠に「H2そのものを不要にはできない」と論じているので、実際の倍率が13.5倍であることは論旨の強さに直接効く。

## D-2 `light_absorption` の維持コストが実質ゼロ

仕様書 §10 は「新しい人工penaltyは追加しない。既存physical basal modelのorgan componentに `light_absorption` が含まれるため、basal organ upkeepが自然に増える」としている。

**方針は正しいが、量が3桁足りない。**

`photon flux = 1.0 µmol/m2/s` での実測:

| light_absorption | absorptance | P_photo | Δcost (organ upkeep増) | benefit/cost |
|---:|---:|---:|---:|---:|
| 0.001 (seed) | 0.100% | 0.0114 fW | 0.00003 fW | **445 : 1** |
| 0.01 | 0.995% | 0.1133 fW | 0.00026 fW | **443 : 1** |
| 0.1 | 9.516% | 1.0838 fW | 0.00256 fW | **424 : 1** |
| 1.0 | 63.212% | 7.1990 fW | 0.02555 fW | **282 : 1** |
| 5.0 (gene max) | 99.326% | 11.3120 fW | 0.12777 fW | **89 : 1** |

損益分岐となる `light_absorption` は **1e-9**。つまり:

> **光がある限り、どんなに小さい `light_absorption` でも、どんなに大きい `light_absorption` でも、常に黒字である。**

理由は明快で、organ upkeepは *reference basal power (0.43 fW) に対する相対値* として定義されているのに対し、入射光は 113.89 fW = **basalの263倍** だからである。upkeep modelはlightがarbitrary単位だった時代に校正されており、lightが今やbasalの2桁上の量になることを知らない。

したがって仕様書§10の

```text
dark environment -> phototrophyはcostのみ
light + H2 -> benefitとcostのtrade-off
```

のうち、**後者のtrade-offは成立しない。** 明るい場所では純粋なfree lunchになる。

## D-3 photon flux 1.0 µmol/m2/s は「弱い補助」ではなく支配的

仕様書 §5.1 は 1.0 µmol/m2/s を「diagnostic / working reference」と正しく留保しているが、§4の「弱いが選択可能な機能として開始する」という記述と実際の量が噛み合っていない。

```text
入射power (1.0 µmol/m2/s, 半径0.49 µm) = 113.89 fW
非phototrophの P_full                   =   0.43 fW   (263倍)
H2 income @ 10 mM source cell           =   6.94 fW
H2 income @ H2場の中央値 566 µM         =   0.94 fW
```

flux感度:

| flux [µmol/m2/s] | seed の P_photo | gene=1.0 の P_photo | vs H2@source | vs H2@中央値 |
|---:|---:|---:|---:|---:|
| 0.01 | 0.00011 fW | 0.072 fW | 0.01x | 0.08x |
| 0.1 | 0.00114 fW | 0.720 fW | 0.10x | **0.77x** |
| **1.0 (仕様書候補)** | 0.01138 fW | 7.199 fW | **1.04x** | **7.66x** |
| 10.0 | 0.11383 fW | 71.99 fW | 10.38x | 76.58x |

**1.0 µmol/m2/s では、進化後のphototrophは世界の中央的なセルでH2収入の7.7倍を光から得る。** これは補助Energy源ではなく主Energy源である。

しかも仕様書 §11 の default pattern は `uniform` なので、この 7.7倍のadvantageは**世界のどこでも同じ**。空間的な差がないので、H2-specialistとphototrophが棲み分ける余地は原理的に存在しない。

なお **光の物理計算自体は正しい。** 1 µmol/m2/s は現生の低光量anoxygenic phototroph (Black Sea chemocline の green sulfur bacteria は約0.01 µmol/m2/s) から見れば十分明るく、1 µm細胞がこれで全代謝を賄えるのは現実的である。問題は光ではなく、**H2側のEnergyが非常に貧しい** (maintenance 0.43 fW / 10 mM vent でも 6.94 fW) ことにある。

仕様書が §5.1 で引用している Overmann et al. 2005 の低光量phototrophの実測レンジ (0.01 µmol/m2/s級) は、**仕様書が採用した 1.0 よりも2桁低い値を支持している。**

## D-4 H2 coupling cap は「nicheが生まれる場所」で binding する

`E_photo = min(L, n_H2 * CAP)` の binding 側:

| 局所H2 | q * CAP | L (gene=1.0) | binding |
|---:|---:|---:|---|
| 50 µM | 1.120 fW | 7.199 fW | **cap** |
| 200 µM | 4.376 fW | 7.199 fW | **cap** |
| 550 µM | 11.410 fW | 7.199 fW | light |
| 1000 µM | 19.449 fW | 7.199 fW | light |
| 10000 µM | 86.429 fW | 7.199 fW | light |

境界は **約550 µM** で、これはbaseline H2場の中央値 (566 µM) とほぼ一致する。

つまり:

```text
H2が濃い場所 (vent近傍)  -> 光bonusが満額出る  ... 一番必要ない場所
H2が薄い場所 (vent遠方)  -> 光bonusがH2に比例して絞られる ... 一番必要な場所
```

**これは狙いと逆向きである。** phototrophyが進化的に面白くなるのは「H2が足りない場所でも生きられる」からであって、「H2が潤沢な場所でさらに効率が上がる」からではない。現在の結合式は、vent近傍にいることの既存advantageを増幅するだけで、新しいnicheを開かない。

これは仕様書のバグではなく、§7の「H2依存を維持する」という要求を最も素直に実装した必然的な帰結である。§4で代替案を示す。

## D-5 `light_absorption` は実験期間内に進化できない

```text
mutation_rate σ = 0.05 (乗算)
加算項SD = additive_mutation_frac(0.01) * σ * GENE_SCALE(0.5) = 0.00025
```

まず良い点: **加算項SDはseed 0.001の0.25倍しかないので、seed値が1世代で消し飛ぶことはない。** 1世代後のq10/q50/q90は 0.00067 / 0.00100 / 0.00133 で、意図どおり弱いseedから始まる。

しかし裏返しに、進化が遅い。**毎世代1σ分だけ有利方向へ動くという最良ケースでも**:

```text
seed 0.001 -> 0.01  (absorptance 1%)   :  46 世代
seed 0.001 -> 0.1   (absorptance 9.5%) :  92 世代
seed 0.001 -> 1.0   (absorptance 63%)  : 138 世代
```

一方、現在の計算予算は:

```text
Exp15/16/17 10日run : max generation 5-6
Exp18 A2            : max generation 6-9
Exp18 20日run       : GitHub Actions 6h上限で未完
```

**2桁足りない。** したがってExp20 Phase B (natural innovation ON/OFF) は、どう設計しても「phototrophyの量的洗練」を観測できない。観測できるのはせいぜい「innovation eventが起きたか」「seed水準のcapabilityが保持されたか失われたか」までである。

さらに innovation供給の問題も残っている (前回レビュー Issue #69 と同じ):

```text
phototrophy_innovation_prob = 1e-4 / birth
10日runの総出生数 ~ 3000
-> 期待 innovation 回数 = 約0.3 回 / run
loss_prob = 1e-3 = innovation_prob の10倍
```

## D-6 CAP = 30 kJ/mol H2 は妥当。ただし導出を書くべき

仕様書 §7.1 は 30000 J/mol を「working value」として置くだけで導出を示していない。検算すると妥当である:

```text
800 nm photon = 149.5 kJ/mol photons
H2 は 2 electrons を供給 -> 1 photon/electron なら投入上限 = 299.1 kJ/mol H2
CAP 30 kJ/mol / 299.1 kJ/mol = 10.0%
```

つまりCAPは「量子 -> usable cellular Energy の変換効率10%」に相当する。これは `phototrophy_radiant_to_usable_eff = 0.10` と同じ10%だが、**意味が違う** (前者は電子供与体1 molあたりの上限、後者は捕捉photonあたりの効率)。両者は `min()` の別の腕なので**二重計上にはならない**。ここは実装が正しい。

ただしこの導出を仕様書に書いておかないと、将来 `radiant_to_usable_eff` を触る人が「10%が2回掛かっているのでは」と誤解する。§7.1へ3行追記することを推奨する。

# 3. 修正推奨

## MUST FIX（実装前に決着が必要）

### R-1 `h2_usable_energy_j_per_mol` の記述を 2407.5 へ訂正する

§1 D-1。仕様書 §7.1 の「3750」「約9倍」を「2407.5」「約13.5倍」へ。

**あわせて `evosim/config.py` のdefault 3750 と実運用値 2407.5 の乖離そのものを解消すべき**である。Exp14で「計画文書の値と実際に走った値が違う」ことで実験1本を失った前例がある。V1.11でlight paramsを追加するときに、physical modeのdefaultをLUCA proxy値へ寄せるか、少なくともconfigに「physical modeではluca.make_cfgが上書きする」旨のコメントを入れること。

### R-2 `light_absorption` に実質的なコストを与える

§1 D-2。organ upkeepは3桁足りず、trade-offが成立していない。

**人工penaltyを足すのではなく、V1.10で手に入れたC/N/Pを使うことを推奨する。**

実際の色素・reaction center機構は細胞タンパク質の大きな割合を占め、bacteriochlorophyllはtetrapyrroleで**1分子あたり4個のN**を含む。したがって:

```text
phototrophy machinery は追加の N (と C) を要求する
-> biomass の実効 N/C 比が light_absorption とともに上がる
-> N が律速な環境では phototroph が不利になる
```

これは:

- 人工penaltyではなく**物理的に正しい**
- V1.10で導入したC/N/P stoichiometryを初めて生態的に意味あるものにする
- Exp17 Phase C1で校正済みのstock倍率 (10x / 30x / 50x) がそのままtrade-offの強さのつまみになる
- **空間的・条件的な分化を生む** — 明るくてN豊富なら phototroph、N貧困なら chemotroph

実装は「`light_absorption` に比例して biomass の N 要求係数を上げる」だけで済み、既存のC/N/P growth limiterにそのまま乗る。

これを入れずにExp20を走らせると、結果は「phototrophyが100%固定した」以外になり得ない。

### R-3 photon flux の reference を 0.01 - 0.1 µmol/m2/s へ下げる

§1 D-3。1.0では光がH2の7.7倍 (中央値セル) になり、補助Energy源ではなくなる。

選び方の基準を明示することを推奨する:

> **進化後phototroph (gene=1.0) の光power が、H2場の中央値セルでのH2収入と同オーダーになるfluxを reference とする。**

この基準だと **0.1 µmol/m2/s** (0.77x) が該当する。仕様書自身が引用している Overmann et al. 2005 の低光量phototroph実測レンジ (0.01級) とも整合する。

Exp20の感度rangeとして `0 / 0.01 / 0.1 / 1.0 / 10.0` を振る計画 (§18) は妥当なので、**referenceを1.0に固定してからExp20で確認するのではなく、Exp20 Phase Aの結果でreferenceを決める**という順序にすべきである。

### R-4 innovation event 供給とExp20 Phase Bの設計が噛み合っていない

§1 D-5。`1e-4/birth × 約3000 births = 0.3 event/run`、`loss_prob` はその10倍。

前回レビュー (Issue #69) と同じ指摘だが、V1.11では追加の問題がある: **`light_absorption` を機能水準まで進化させるには最良ケースでも46-92世代必要で、現在の計算予算は5-9世代**。

したがってExp20 Phase Bは「自然発生するか」しか問えない。それ自体は正当な問いだが、**そう明記すべき**である。「phototrophyが進化して定着するか」を問うのは、計算基盤が整うまで保留する。

`phototrophy_innovation_prob` を上げるのは HARD RULE 6 に抵触するので推奨しない。代わりに §5 の実験設計変更 (seeded invasion arm) を推奨する。

### R-6 piecewise branch の選択条件を仕様へ明記する

§8.1の2分岐は、**どちらの分岐を使うかの判定条件を書いていない**。実装者が間違えやすい箇所なので明記すべき。

```text
branch 1 (q <= L/C):  q_req = H / (B + C)
branch 2 (q >= L/C):  q_req = (H - L) / B

分岐条件:  H <= L * (B + C) / C  なら branch 1、そうでなければ branch 2
```

この閾値は両分岐で厳密に一致する (連続) ので、境界での不連続は生じない。`H < L` のとき branch 2 は負の `q_req` を返すが、上の条件により branch 1 が選ばれるので問題にならない。**「H < L なら q=0」と実装してはいけない** — その場合 `n_H2 = 0` になり、T3 (H2-zero) の規則により photo bonus も 0 になって、光が強いほど何も得られないという逆転が起きる。

# 4. 設計の代替案 — 結合点をATPではなくreducing powerへ

§1 D-4 が示した「H2が薄い場所でこそ光bonusが消える」問題は、結合式の係数ではなく**結合する場所**に由来する。

## 4.1 現実の anoxygenic phototrophy はどう分かれているか

purple bacteria / green sulfur bacteria の光独立栄養では:

```text
光  -> cyclic photophosphorylation -> ATP           (電子供与体と化学量論的に独立)
H2  -> hydrogenase -> quinone pool -> 逆電子伝達 -> NAD(P)H  (還元力)
NAD(P)H + ATP -> CO2固定 -> biomass
```

つまり **ATPは光から、還元力は電子供与体から** 得ている。ATP生成量はphoton数で決まり、H2のmol数では決まらない。

仕様書 §8 の `E_photo = min(L, n_H2 * C)` は、ATP生成をH2 molへ縛っている。これは「H2なしでは何も得られない」を保証する最も直接的な方法だが、現実の共役構造とは違い、しかも§1 D-4の逆向きな帰結を生む。

## 4.2 代替案

```text
光         -> usable Energy (ATP相当) を直接生成。H2非依存。
H2         -> usable Energy (現行どおり) + biomass合成に必要な還元力
biomass成長 -> H2 uptake が無いと不可能
```

実装は既にある仕組みで書ける。V1.10でgrowthはC/N/Pを同時に満たす範囲でしか進まないので、そこへ**「還元力」= H2由来という第4の制約**を足すだけでよい。

```text
growth_possible_biomass = min(energy制約, C制約, N制約, P制約, H2由来還元力制約)
```

## 4.3 何が変わるか

```text
                    現行仕様(§8)              代替案
light only          Energy 0 / 死               maintenance は払える / 成長不可
H2 only             現行どおり                  現行どおり
light + H2          H2濃度に比例したbonus        光でmaintenanceを賄い、H2を全部成長へ回せる
H2希薄 + light      bonusがほぼ消える            生存できる (成長はしない)
```

**HARD RULE 3「光だけでEnergyを得られる経路を作らない」の意図は保たれる。** 仕様書がこのルールを置いた理由は §7 に明記されており、「電子供与体なしのphotoautotrophyが成立してしまう」ことを防ぐためである。代替案では **光だけでは成長も繁殖もできない** ので、photoautotrophyは成立しない。禁じているのは独立栄養であって、光による維持ではない。

## 4.4 なぜこれが V1.10.1 と噛み合うのか

ここが重要である。**Exp18で作ったdynamic ventが、代替案では初めて意味を持つ。**

Exp18の結果:

```text
A1 (6h ON / 6h OFF)      : 3/3 絶滅 — 時間変動が強すぎる
A2 (48hごとに1 vent移動)  : 3/3 生存、個体数は大幅減、世代は深い
A3 (両方)                : 生存限界、別seedで5/5絶滅
```

A1が全滅した理由をExp18は「現在の祖先は長時間のsource interruptionへ追従・耐久する能力が不足している」と診断している。**まさにその能力が、光によるmaintenanceである。**

```text
現行仕様: vent が消える -> H2 が消える -> 光bonusも消える -> 一緒に死ぬ
代替案  : vent が消える -> H2 が消える -> 光で maintenance は払える
          -> 次の vent へ到達するまで生き延びられる
```

つまり代替案では:

- **A1 (temporal) が「強すぎる環境」から「phototrophyへの選択圧」に変わる**
- phototrophが chemotroph を出し抜く条件が、環境の時間構造から自然に出てくる
- 明るくH2が途切れる場所では phototroph、暗くH2が安定な場所では chemotroph という**分化が成立しうる**
- 「常に固定勝利しない」というPhase 1 close条件を、環境側の構造だけで満たせる

現行仕様ではこれが起きない。光bonusはH2 uptakeに比例するので、H2が消えれば光の価値も消えるからである。

## 4.5 判断

**代替案を強く推奨する。ただしこれは仕様の骨格変更なので、人間judgementの対象である。**

採らない場合でも、少なくとも §1 D-4 (cap が H2希薄域で binding する) を仕様書へ既知の制約として明記し、**Exp20の解釈時に「phototrophyはvent近傍でしか有利にならない」ことを予測として事前登録**すべきである。

# 5. Exp20 への提案

仕様書 §18 は Phase 0 / A / B の3段構成を挙げている。骨格は妥当。以下を追加・変更する。

## 5.1 追加すべき: Phase A2 — seeded invasion arm【最も費用対効果が高い】

§1 D-5 のとおり、自然innovationは 0.3 event/run しか出ず、`light_absorption` は5-9世代では動かない。この2つの制約下で **測れる量が1つだけある: invasion fitness** である。

```text
t=0 で population の一定割合を phototroph として配置する
  seeded fraction = 1% / 10% / 50%
  light_absorption は固定 (0.001 / 0.01 / 0.1 / 1.0 を別armで)
数世代のあいだの phototroph 頻度の変化率を測る
```

これは:

- **稀事象ではなく速度を測る**ので、統計的検出力が桁違いに高い
- 5-9世代で十分に測れる (頻度変化は世代あたりで出る)
- 「設計者がphototrophを置いた」ことにならない (置いたのは初期条件であって適応度関数ではない)。`絶対設計原則` に抵触しない
- **R-2 (N cost) と R-3 (flux) の校正に直接使える** — 頻度変化率が0付近になるfluxとNコストの組合せが、trade-offが成立する領域である
- 50% seeded arm は **頻度依存性** を検出できる (1%と50%で符号や大きさが変われば、単純なsweepではない)

Phase B (natural innovation) より先にこれを走らせることを推奨する。Phase Bは「自然に出るか」の確認であり、**出た後どうなるかはPhase A2でしか測れない**。

## 5.2 Phase A (forced phototroph, flux sensitivity) を最優先にする

仕様書 §18 の Phase A は妥当で、しかも安い (固定表現型、短期間)。ここで:

```text
photon flux : 0 / 0.01 / 0.1 / 1.0 / 10.0 µmol/m2/s
light_absorption : 固定値を数点
```

を振り、**§1 D-3 の表 (光power vs H2 power) を実測で確認してから reference flux を決める** (R-3)。

Exp20全体の中でここが唯一「physical response curveを取る」段階なので、seed数を増やすよりflux/absorption gridを密にするほうが価値が高い。

## 5.3 Phase 0 に追加すべきcontrol

仕様書 T1-T10 に加え、**生態レベルのnegative control**:

```text
P0-a: physical_light_enabled=True, 全個体 phototrophy OFF, 10日
      -> V1.10.1 A0 と個体数・世代が統計的に区別できないこと
      (photon field の追加が H2 生態へ副作用を持たないことの確認)
```

これは T12 (bitwise一致) の生態版で、実装ミスではなく**Config経由の意図しない相互作用**を検出する。

## 5.4 Phase B は「供給」だけを問う実験として再定義する

§1 D-5 と R-4。Phase Bで問えるのは:

```text
Q: 現在の innovation_prob / loss_prob / run長で、phototrophy capability が
   出現し、seed水準のまま保持されるか
```

であって、「phototrophyが進化するか」ではない。**この限定を計画文書へ明記**し、結果考察で拡大解釈しないようにする。

期待される結果を事前登録しておくことも推奨する:

```text
期待: 10日 x 5 seeds で innovation event は合計 1-2 回程度。
      capable fraction は中立平衡 9% には遠く及ばない。
      「innovationが観測されなかった」も正式結果として記録する。
```

## 5.5 削ってよいもの

- **long-run な進化 run** — §1 D-5 のとおり2桁足りないので、計算基盤が整うまで走らせる価値がない。
- **flux と light_absorption の細かい最適値探索** — `環境因子追加・校正方針` §3.1 のとおり。response curveの形が分かれば十分。
- **day/night を V1.11 の最初の validation に入れること** — 仕様書 §11 が既に「最初のmechanical validationではOFF」としており正しい。維持すべき。昼夜を入れると光の効果と時間構造の効果が交絡する。

# 6. Exp18 / Exp19 への考察

## 6.1 Exp18 の最大の成果は A0 vs A1 である

**「H2の総供給量を完全に一致させたまま、時間構造だけで 3/3 生存 → 3/3 絶滅 が反転した」**というのは、このプロジェクトで最も強い単一の結果だと考える。Phase 0で積算source molが完全一致していることまで示しているので、交絡の余地がない。

これは `長期ロードマップ` の「供給の時間・空間構造そのものが選択圧になる」という主張の、初めての決定的な証拠である。V1.11の設計判断 (§4.4) にも直結する。

## 6.2 A3選択は「事前登録どおり」だが、gateの設計に問題があった

Phase Aは seeds 18001-18003 (n=3) で A3 が 2/3 生存し、事前登録gateを満たしたのでPhase Bへ採用された。しかしPhase Bの別seed集合 (18101-18105) では 5/5 絶滅した。

Exp18の結果考察はこれを「A3は生存限界環境」と正しく診断している。ただし**より一般的な教訓を引き出すべき**である:

> **n=3 の二値outcomeで arm を選択するgateは、統計的検出力がほぼ無い。**

3 seedで「2/3生存」は、真の生存確率が20%〜90%のどこでも整合する。そこから**最も過酷なarmを選ぶ**ルールを組み合わせると、選ばれるのは「たまたま当たった限界条件」になり、必ず回帰する。これは選択バイアスの教科書的な例である。

推奨する恒久ルール:

```text
1. arm選択gateは「通過したうち最も過酷なarm」ではなく
   「マージンが最も広いarm」を選ぶ
2. または、選択後に同じarmを別seedで再確認してからPhase Bへ進む (安い)
3. n<5 の二値outcomeでarm選択をしない
```

A2は 3/3 生存で、A0との差も十分大きかった。**A2を選んでいれば Phase B は完走できた可能性が高い。** Exp19がA2を採用したのは正しい判断である。

## 6.3 計算基盤が次のボトルネックである — V1.11で悪化する

Exp18 Phase B static側が 6h上限で cancel されたのは、個体数が数千規模で長期維持されたためである。

**V1.11ではこれが悪化する。** phototrophyが定着すると (§1 D-2/D-3 のとおり、現在の数値では確実に定着する) Energy収入が増え、個体数はC/N/P上限まで押し上げられる。つまり:

```text
phototrophy成功 -> 個体数増 -> wall-clock増 -> run未完
```

という、**科学的成功が計算失敗を招く**構造になっている。

推奨:

1. **Exp20はすべて 6h以内に完走する設計にする** (Exp19が既にそうしているのは正しい)。Phase A / A2 はどちらも短期で足りる。
2. **checkpoint / resume を V1.11 実装と同時に入れる**ことを検討する。V1.11のcode変更はどのみち `simulation.py` に触るので、ついでに入れるコストが最も低いタイミングである。
3. **`max_population_halt` と生態学的上限の分離**を記録に残す (前回レビュー L-7)。個体数が増える方向の変更を入れる直前なので、今が最後のタイミング。

## 6.4 H2の生物的消費は V1.10.1 でも無視できるままの可能性が高い

V1.10.1のfinite-flux化は、sourceを監査可能にしEexp18の時間変動操作を可能にした点で大きな前進である。ただし **F0 は旧Dirichlet環境の定常状態を再現するよう校正されている** (Phase 0で測定した `F0 = 4.89e-11 mol/s/vent`) ので、H2場そのものは以前とほぼ同じはずである。

Exp16 §7.1 で測定された `biological uptake / source influx = 5.6e-6` は、finite-flux化しても大きくは変わらないと予想する。つまり **H2資源競争は依然として存在しない。**

これはV1.11に直接効く。仕様書 §8 の結合式では、**phototrophはH2を節約する** (同じEnergyを得るのに必要なH2が減る) ので、本来なら「phototrophが増えるとchemotrophにH2が回る」という負の頻度依存が働き、共存が安定する。しかしH2が枯渇しないなら、**この安定化機構は完全に不活性**である。

Exp19はすでに `H2 source/loss/biological uptake ledger` をreadoutに含めている。**Exp19の結果が出たら、まずこの比を見ることを推奨する。**

```text
biological uptake / source influx が
  ~1e-5 のまま -> H2競争なし。V1.11のH2節約効果は生態的に無意味。
                  phototrophyのsweepを止めるものは何も無い (R-2のNコストが必須)
  1e-2 以上    -> 競争が成立。負の頻度依存が期待でき、共存の可能性が出る
```

これは追加の実験を要さず、既存readoutの読み方の指定だけで済む。

## 6.5 Exp19 の設計は妥当

2×2 (STATIC/A2 × FIXED/EVOLVE)、同一seedを4 armで対応、10日、3 seeds という設計は、計算制約下での判断として正しい。特に:

- **Comparison B (E1 vs E3)** を置いて「A2特有か一般的ドリフトか」を分離する設計は良い
- **形質の方向をPASS条件に事前固定しない**判断 (§11) は正しい。V1.8で一度通った道を避けている
- 「変化がないことを正式結果として記録できる」を成功条件に含めている点も良い

1点だけ: **3 seedsは §6.2 と同じ検出力の問題を持つ。** Exp19は arm選択をしないので §6.2 ほど危険ではないが、「3/3 seedsで storage_capacity 増加」のような読み方をする場合は、3 seedでの符号一致は偶然でも 1/8 = 12.5% で起きることを結果考察に明記しておくべきである。

# 7. まとめ

**V1.11の設計思想は正しく、前回レビューで指摘したlight物理スケール化の問題に正面から答えている。** ロードマップの順序変更 (CNP → dynamic vent → phototrophy) も良い判断で、Exp18のA0 vs A1はこのプロジェクト最強の結果である。

ただし候補値を実baselineへ当てると、**V1.11が狙っている「環境条件に応じて増減する進化可能なstrategy」は現在の数値では成立しない**。

```text
コストが実質ゼロ (benefit/cost 89:1 - 445:1)
+ 光が空間的に一様
+ 光がH2の7.7倍 (中央値セル)
= 確実なsweep、分化なし
```

実装前に決着すべきは3つ:

```text
R-1  h2_usable_energy_j_per_mol を 2407.5 へ訂正 (「9倍」-> 13.5倍)
R-2  light_absorption に N コストを与える (人工penaltyではなくC/N/P経由)
R-3  photon flux reference を 0.1 µmol/m2/s 前後へ下げる、
     または Exp20 Phase A の結果で決める
```

加えて、結合点をATPからreducing powerへ移す代替案 (§4) を人間judgementに委ねたい。**これを採ると、Exp18で「強すぎる」と判定されたA1環境が、そのままphototrophyへの選択圧に変わる。** V1.10.1への投資が最大限に活きる設計である。

実験側は、Phase A (flux感度) と新設の Phase A2 (seeded invasion) を先に走らせることを推奨する。自然innovationは 0.3 event/run、`light_absorption` の進化には46-92世代必要で計算予算は5-9世代なので、**測れる量はinvasion fitnessだけ**である。
