# 1. ① `e = E/E_max` はリザーブが減っても動かない ★最重要

## 1-1. 事実

`docs/V1.9_iLUCA再設計仕様.md` の3つの規定を重ねると、`E` の値が構造的に固定される。

```text
§6.2  行動決定前に  E < E_target かつ R > 0  なら E_target まで R から補充
§6.1  gain は  ① E を E_target まで  ② 余りを R へ  ③ R 満杯後に E を E_max まで
§7    e = clip(E / E_max, 0, 1)
      activity = activity_floor + (1-activity_floor) * e**s
```

したがって:

| リザーブの状態 | `E` の値 | `e = E/E_max` | `activity` |
|---|---|---|---|
| R 満杯 | `E_target` 〜 `E_max` | 0.5 〜 1.0 | 0.55 〜 1.0 |
| **0 < R < R_max** | **`E_target` へ固定** | **0.5 へ固定** | **定数** |
| R = 0 | 自由落下 | < 0.5 | 低下 |

**リザーブが満タンから空へ減っていく全区間で `e` は 0.5 に貼り付く。**
残り備蓄が80%でも1%でも `activity` は同じ値になり、
飢餓応答が効き始めるのは `R` が厳密に0になった瞬間、つまり手遅れになってからである。

`evosim/simulation.py` の `step()` のtick順を確認した。

```text
3. decide_and_move   ← §6.2 の mobilization はここの直前
5. _absorb_fields    ← credit_energy
6. maintenance + repair → if org.energy <= 0.0: _kill(starvation)
```

`decide_and_move` の直前に `E` を `E_target` へ揃えるので、
**`activity` が計算される瞬間の `e` は厳密に 0.5 である。**

## 1-2. 帰結 — `starvation_sensitivity` が意図と別の意味を持つ

初期値 `starvation_sensitivity = 1.0`、`activity_floor = 0.10` を入れると:

```text
activity = 0.10 + 0.90 * 0.5^1.0 = 0.55
```

**十分に餌のある個体が、永久に55%の活動で動き続ける。**

さらに `s` が進化すると:

```text
s=0 -> activity 1.00   (応答なし)
s=1 -> activity 0.55
s=2 -> activity 0.325
s=4 -> activity 0.156  (GENE_MAX)
```

`e` が情報を持たないので、**`s` は「飢餓への応答の強さ」ではなく
「恒常的にどれだけ鈍いか」を決めるだけの遺伝子になる。**

V1.9 baseline（H2 が vent へ局在する patchy world）での選択方向を見積もると:

```text
s=1 の節約  BMR可変部 0.15×0.45 = 0.0675
            movement  0.0405×(1-0.55²) = 0.0282
            repair    0.05×0.45 = 0.0225
            計 約 0.118 E/tick  (維持費 0.494 の約24%)
s=1 の損失  移動速度 55% -> vent到達が遅い
```

平衡個体数は vent 近傍に集中するので、**既に vent 上にいる個体にとって
`s` を上げるのは純粋な得**である。したがって `s` は上限方向へ選択され、
集団全体が恒常的に最大限鈍い状態へ向かうと予測する。

**いずれにせよ「飢餓応答」としては機能しない。**

## 1-3. 変更提案

```text
現状: e = clip(E / E_max, 0, 1)
提案: e = clip((E + R) / T_max, 0, 1)
```

これで備蓄の枯渇に対して滑らかに応答する。
ただし単独で入れると、`reserve_capacity` が大きい個体ほど `T_max` が大きく、
同じ絶対備蓄でも `e` が小さく出るという歪みが残る。**②と組で入れる必要がある。**

より頑健な代替として、無次元化を capacity ではなく**支出**で行う案も挙げておく。

```text
e = clip( (E + R) / (k * current_maintenance_rate), 0, 1 )
```

これは「今の支出ペースであと何tick生きられるか」という
次元的に意味のある飢餓シグナルで、capacity 遺伝子に依存しない。
`k` は世界定数（例: 100 tick 相当）。実装コストは同程度である。

# 2. ② `reserve_capacity` にコストが無く境界へ張り付く

## 2-1. 文書間の矛盾

```text
docs/V1.9_現状ステータス.md P1 : 「reserve維持コストを持たせるか」= 未決
docs/V1.9_iLUCA再設計仕様.md §8: 「reserve容量だけに人工的なfitness penaltyを追加しない」= 決定済み
```

**ステータス doc が未決としている項目を、仕様書が既に決めている。** まずここを揃える必要がある。

## 2-2. §8 の trade-off は成立しない

§8 は「storage/mobilization loss と繁殖遅延に任せる」としているが:

- **storage loss は通過量にかかるコストで、容量を持つこと自体はタダ**である
  （`reserve_store_eff=0.90` / `reserve_mobilize_eff=0.95` はどちらも流量に対する係数）
- 繁殖遅延は `T >= theta * T_max` 経由で効くが、
  **`theta` も遺伝子なので下げれば相殺できる**（§9）

したがって `reserve_capacity` → `GENE_MAX(5.0)`、`theta` → 低め、
という**境界アトラクタ**になると予測する。
V1.7 で `body_size` が下限 0.2 へ張り付いたのと同じ構造である。

## 2-3. 変更提案

既存の `organ_upkeep` と同じ形の維持費を置く。

```text
reserve_upkeep * genome[reserve_capacity] * matter
```

貯蔵多糖は体積を占め、代謝回転を必要とする。
**人工ペナルティではなく生理則からの導出**なので、絶対原則4（コストは物理・生理則から）
および原則8（特定生態型へ直接ボーナスを与えない）に抵触しない。

これを入れると①の `e = (E+R)/T_max` 案の歪みも抑えられる
（capacity を無闇に増やすと維持費で損をするため）。

# 3. ③ H2-only baseline の個体数が V1.9 の看板目標に対して小さい

**これは `docs/V1.9_現状ステータス.md` の P1〜P5 に入っていない論点である。**

## 3-1. 平衡個体数の検算

供給側（§11 の provisional 値）:

```text
h2_vent_flux 16.0 × 4 vent            = 64.0 substrate/tick
× h2_energy_yield 1.0                 = 64.0 E-equivalent/tick
× h2_conversion_efficiency 0.60       = 38.4 usable E/tick
```

需要側（§4 の initial genome、`light_absorption=0` / `predation_efficiency=0`、
`corpse_digestion=0` と仮定、M=1、activity=1）:

```text
bmr       0.15 + 0.15         = 0.300
organ     0.05 × 1 × 1.5      = 0.075      (chem 1.0 + nutrient 0.5)
sense     0.02 × 0.4²         = 0.0032
membrane  0.03 × 0.5          = 0.015
resist    0.02 × 0.5          = 0.010
move      0.05 × 0.9²         = 0.0405
repair                        ≈ 0.05
                          計  ≈ 0.494 E/tick
```

```text
平衡個体数 ≈ 38.4 / 0.494 ≈ 78 個体
```

Exp11 の B2（chemical-only、約90個体）と同じ regime である。

## 3-2. 看板目標との衝突

V1.9 の中心的な問いは「`light_absorption = 0` から phototrophy が創発するか」である。
§14 の新スケールで最初の加算変異が起きたときの選択係数を見積もると:

```text
additive sigma = additive_mutation_frac(0.01) × mutation_rate(0.05) × GENE_SCALE(5.0)
               = 0.0025
最初の正の値      a ≈ 0.0025
利得              2.0(coef) × 0.0025 × A_eff × H ≈ 0.003 E/tick
コスト            organ_upkeep 0.05 × 1 × 0.0025 = 0.000125
純利得            ≈ 0.0029 E/tick
選択係数 s        ≈ 0.0029 / 0.494 ≈ 0.6%

ドリフト閾値      1/(2N) = 1/(2×78) ≈ 0.64%
```

**`s ≈ ドリフト閾値`。ちょうど境界上である。**

N=800 規模の光世界なら `1/(2N) ≈ 0.06%` で明確に選択されるが、
**V1.9 の baseline は N≈80 の世界**である。
つまり「創発するか」の答えが、生物学ではなく**個体数で決まってしまう**危険がある。

なお、いったん確立すれば乗算変異（σ=0.05 で1世代約5%）が効くので、
`0.0025 → 0.3` の到達自体は約96世代で済む。**律速は最初の確立である。**

## 3-3. 変更提案

§14 は「実装前/直後に解析的または軽量Monte Carloで待ち時間を確認する」としている。
**これを実装前の HARD GATE へ格上げする**ことを提案する。

そして待ち時間が予定 run 長を超える場合、**変異スケールをいじるより
H2 供給を増やして N を上げるほうが筋が良い**。
変異スケールを触ると全遺伝子の進化速度が変わる（§4-5 参照）。

# 4. `docs/V1.9_現状ステータス.md` §8 の6項目への回答

## Q1. P1〜P5 に抜けている重大な設計課題はないか

§3 の N 問題に加えて2つある。

### 4-1-a. 容量縮小オーバーフローの処理箇所が1つ抜けている

§9.2 は繁殖時の親の overflow を扱っているが、**同じ状況がもう1箇所ある。**

```python
# evosim/simulation.py  _bite() 内
t_emax = target.energy_max(cfg.energy_capacity)
if target.energy > t_emax:
    self.energy_out_cum += target.energy - t_emax   # 熱として散逸
    target.energy = t_emax
```

捕食で噛まれた側は matter が減るので `E_max` が下がる。
2-pool 化すると「`E` の超過分は `R` へ回す」が正しい挙動になるので、
ここも §9.2 と同じ helper を通す必要がある。

`matter` が減る箇所は「繁殖」と「捕食で噛まれる」の2つだけなので、
**capacity 縮小時の再配分を helper 1本へ集約する**のが安全である。

### 4-1-b. 「R > 0 なのに餓死する」を禁止する不変条件がない

tick順は次のとおりである。

```text
step 3: decide_and_move   ← §6.2 の mobilization はここで1回だけ
step 5: _absorb_fields
step 6: maintenance + repair → if org.energy <= 0.0: _kill(starvation)
```

**mobilization は1 tickに1回しか走らず、maintenance はその後に引かれる。**
現在の provisional 値（`E_target = 0.5 × 20 × M = 10M`、maintenance ≈ 0.5/tick）なら
実際には起きないが、**構造的には保証されていない。**

`birth_overhead = 2.0` は `E_target = 10` の20%にあたるので、
後で `operational_energy_capacity` を下げると顔を出す。

→ 死亡判定の直前に mobilization をもう一度通し、
**`E ≤ 0 かつ R > 0` で餓死しないことを unit test で固定する**ことを提案する。

## Q2. 2-pool 化は既存の conservation / reproduction / death と矛盾しないか

**矛盾しない。ただし触るべき箇所が §20 / §21 のリストより多い。**

`system_energy()` へ `sum(o.reserve)` を足すのは §20 のとおりで正しい。
加えて次を確認した。

```python
# evosim/simulation.py  _kill()
if org.energy < 0.0:
    # コストは全額散逸として計上済みだが、実在したのは残額のみ。
    self.energy_out_cum += org.energy   # 過剰計上分を台帳へ戻す
    org.energy = 0.0
```

この負値補正は `org.energy` 単独を前提にしているので、
**E/R 合算で書き直さないと台帳が閉じない。**

まとめると、2-pool 化で必ず触る必要がある箇所は:

```text
system_energy()          reserve を加算
_kill()                  負値補正を E/R 合算へ
_try_reproduce()         §9.2 のとおり（仕様済み）
_bite()                  capacity 縮小 overflow（仕様漏れ / 4-1-a）
全 gain 経路             credit_energy() 経由（仕様済み）
```

## Q3. 飢餓応答を baseline 機能として与え、応答特性を遺伝化する方針は妥当か

**妥当。強く支持する。** ただし §1 の修正が前提である。

境界の引き方も正しい。入力が「自分の現在の内部状態」だけなら、
周期環境でも内部時計は**原理的に発生しない**（時刻情報がどこからも入らないため）。
「夜だから休む」ではなく「減ったから絞る」に限定されている限り、絶対原則12は守られる。

ただし2点、追加の指摘がある。

### 4-3-a. 隠れたフィードバックループ

§7.1 は「uptake capacity へは activity を掛けない」と明示しているが、
`repair` には掛けている。すると次の経路で間接的に取得能力が落ちる。

```text
activity↓ → repair↓ → damage蓄積 → phi↓ → uptake↓ かつ v_max↓ → さらに飢餓
```

`phi = max(phi_floor, 1 - D/(damage_capacity·M·(1+dr)))` で、
M=1・無修復なら damage は 0.02/tick、`D_max = 15` なので
100 tick で phi ≈ 0.87。致命的ではないが長期飢餓では効く。

**`repair` を activity 対象から外す**のも選択肢である。

### 4-3-b. `movement` への activity 適用は V1.9 baseline では逆効果になりうる

V1.8 の夜（光がどこにも無い）では「動かない」が正解だった。
しかし **V1.9 の baseline は H2 が vent へ局在する patchy world** である。
そこで飢餓時に動きを止めると vent へ辿り着けない。

節約額の内訳（M=1、s=1、activity=0.55）:

```text
BMR可変部  0.0675   ← 節約の 57%
repair     0.0225   ← 19%
movement   0.0282   ← 24%
```

**movement は節約額の1/4しか占めないのに、探索不能のリスクを100%背負う。**

→ **V1.9 では activity を BMR 可変部だけに掛け、
movement への適用は昼夜が復帰する版へ回す**ことを提案する。

## Q4. H2 explicit / CO2 implicit の V1.9 スコープは粗すぎないか

**粗すぎない。V1.9 としては正しい判断である。**

化学合成の科学的中身のうちこのモデルに効くのは
「エネルギーが、局在して枯渇する基質からの反応で得られる」という構造であり、
H2 explicit はそれを捉えている。
CO2 を explicit にすると carbon field + 炭素保存則という Matter モデル全体の変更になり、
絶対原則9（原則1軸ずつ）を大きく超える。

ただし副作用を1つ意識しておくべきである。

**CO2 が無限にあるということは、エネルギー獲得と炭素（Matter）獲得が
化学量論的に切り離されるということである。**
実際のアセトゲンは同じ反応から炭素とエネルギーを得るが、
このモデルでは H2 と `nutrient` が独立軸になる。

Exp13 の解析で見えた「matter の再成長が繁殖を律速する」挙動はこの切り離しの帰結なので、
V1.9 でも残る。**V1.9 で直す必要はないが、「既知の単純化」として文書へ残す価値がある。**

もう1点、`h2_energy_yield = 1.0` は実際の ΔG とは無関係の実装参照値である。
「H2」という実在の化学種名を使う以上、
**"localized reduced substrate" のラベルであって
H2 + CO2 → 酢酸 の熱力学を主張するものではない**と明記しておくと、後で誤読されない。

## Q5. zero 能力から新能力を continuous gene の延長で扱うべきか

**V1.9 では yes。** `unlocked=True` のような離散フラグを入れないのは
絶対原則2（種クラスを作らない）・原則10（遺伝子の存在と進化経路の成立を区別）と整合する。

**ただし §14 の `GENE_SCALE = GENE_MAX - GENE_MIN` への一律変更には反対する。**

これは0から始める遺伝子だけでなく**全遺伝子の加算変異を最大10倍にする。**

| 遺伝子 | range | 現行 `GENE_SCALE` | 新 `GENE_SCALE` | 倍率 |
|---|---|---:|---:|---:|
| `body_size` | 0.2–10.0 | 1.0 | 9.8 | **×9.8** |
| `mutation_rate` | 0.005–0.5 | 0.05 | 0.495 | **×9.9** |
| `reproduction_investment` | 0.05–0.9 | 0.4 | 0.85 | ×2.1 |
| `light_absorption` 他 | 0.0–5.0 | 0.5 | 5.0 | ×10 |

とくに **`mutation_rate` 自身のノイズが10倍**になるのは、進化動力学を不安定にしかねない。
また V1.7 / V1.8 との比較可能性も失われる。

→ **0 から始める遺伝子（`light_absorption` / `predation_efficiency` / 必要なら `corpse_digestion`）
だけスケールを上げる**か、per-gene の明示テーブルにするのが、1軸ずつの原則に沿う。

## Q6. 実装前に追加でコード実査・短期 probe すべき点

3. **`theta`（`reproduction_threshold`）の下限を決める前に、r選択の暴走を検算**（下記 §5-1）

# 5. その他の指摘

## 5-1. `theta` が下限へ落ちると V1.8 の失敗が再現する

`reproduction_threshold` を遺伝化するのは正しい。
しかし**穏やかな環境では「余剰が出たら即分裂」が常に有利**なので、`theta` は下限へ向かう。
それはまさに V1.8 で全滅を起こした圧力弁そのものである。

`GENE_MIN = 0.35` という提案値は、`T_max = 100M` に対して 35M。
V1.8 相当の `0.6 × E_max(100M) = 60M` より**低い**ので、
下限へ張り付いた集団は V1.8 baseline より繁殖が早い＝備蓄しない個体群になる。

夜や飢餓が `theta` を押し上げる、という綱引きが V1.9 の中心的な読みどころなので、
**`theta` の実測値が V1.9 の主要な readout** になる。

`docs/V1.9_現状ステータス.md` P3 には
「threshold が見る Energy は `E` のみか `E+R` か」はあるが、
**「下限をどこに置くか」「下限へ張り付いたら何を意味するか」が抜けている。**
事前登録しておくことを提案する。

## 5-2. V1.7 の `bmr_core = 0.15` は再解釈が必要

`activity` が BMR の可変部を抑制できるようになると、
V1.7 が「常に全額かかる BMR」の下で選定した値ではなくなる。

```text
V1.7選定時   BMR = 0.15 + 0.15 × M^0.75           (常に全額)
V1.9         BMR = 0.15 + activity × 0.15 × M^0.75 (可変)
```

再調整はしなくてよいと思うが、**`body_size` の平衡は動く**ので、
V1.7 の結論（`bmr_core=0.15` が下限張り付きを解除する最小値）を
そのまま引き継がないことを明記すべきである。

## 5-3. `satiety_energy_frac = 0.85` の意味が変わる

`E_max` が `100M → 20M` になり、gain は `E` を `E_target(=10M)` までしか埋めないので、
**`R` が満杯になるまで満腹判定（`0.85 × 20M = 17M`）に到達しない。**

「満ち足りたら停止する」挙動が、事実上「備蓄も満タンになったら停止」へ変わる。
良い方向の変化だと思うが、無自覚だと後で挙動を誤読する。
§17（motility / sensing）へ1行入れておくとよい。

## 5-4. `initial_reserve_frac = 0.50` と①の相互作用

§15 は `E0 = 0.5 × E_max`、`R0 = 0.5 × R_max` で開始する。
`E0` は `E_target` と厳密に一致するので、**開始直後から `e = 0.5` に貼り付く。**

①を直さない限り、**シミュレーション開始の瞬間から全個体が `activity = 0.55` で始まる。**
初期条件の設計としては綺麗だが、①の症状を最初から最大化する組み合わせでもある。
