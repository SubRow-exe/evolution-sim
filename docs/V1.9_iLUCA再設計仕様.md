更新: 2026-09-04
状態: **DESIGN DRAFT / 実装前 / HUMAN DECISION項目あり**

V1.9の目的は単なるphototrophy起源実験ではない。

> **より生物学的に妥当なchemical-first iLUCA baselineを作り、環境側を生存に合わせて曲げずに、内部状態・貯蔵・繁殖戦略が自然選択へ応答できる世界へ作り直す。**

# 1. 科学的前提

V1.9では「LUCAにあったと確定した全機構」を分子レベルで再現しない。

採用原則:

```text
比較的支持が強い構造       -> baselineへ
不確実だが普遍的な生理原理 -> coarse-grained baselineへ
不確実な具体機構           -> 固定しない / 後回し
後発能力                     -> 初期値0、進化可能にする
```

2024年のLUCA再構築では、LUCAはprokaryote-grade anaerobic acetogenで、H2利用・Wood-Ljungdahl pathway・ATP synthaseが強く支持され、photosynthesisの支持はほぼ無い。

主要参考:
- Moody et al. 2024, Nature Ecology & Evolution, DOI: 10.1038/s41559-024-02461-1
- Weiss et al. 2016, Nature Microbiology, DOI: 10.1038/nmicrobiol.2016.116

温度最適・具体的な運動装置・具体的なstorage polymer等はLUCAについて不確実なのでV1.9で断定しない。

# 5. 2-pool Energy model

個体状態を:

```text
energy   = operational Energy E
reserve  = stored Energy R
```

へ変更する。

`Organism.__slots__`へ`reserve`を追加する。

## 5.1 capacity

```text
E_max = operational_energy_capacity * matter
R_max = reserve_capacity_coef * genome[reserve_capacity] * matter
T_max = E_max + R_max
```

provisional Config:

```text
operational_energy_capacity = 20.0
reserve_capacity_coef       = 80.0
```

initial reserve_capacity=1なら、matterあたり総capacityは旧`energy_capacity=100`と同じ100を維持する。
これは最終生物定数ではなく、V1.8からの数値scaleを壊しすぎないimplementation reference。

旧`energy_capacity`はV1.9でdeprecatedとし、新コード内部では使わない。

# 6. Energy buffer / reserve自動制御

これは未来予測ではなく現在の内部状態だけを使う恒常性。

Config provisional:

```text
energy_buffer_target_frac = 0.50
reserve_store_eff          = 0.90
reserve_mobilize_eff       = 0.95
```

```text
E_target = energy_buffer_target_frac * E_max
```

## 6.1 Energy取得時 `credit_energy(org, gain)`

順序を固定する。

```text
1. E < E_targetならE_targetまでoperationalへ
2. 残りをreserveへ保存 (store efficiency適用)
3. reserve満杯後の残りをE_maxまでoperationalへ
4. それでも余ればheatとして散逸
```

storage conversion lossは`energy_out_cum`へ記録する。

光・H2・死骸・捕食等、Energy gainは原則このhelperを通す。

## 6.2 reserve mobilization

各個体の行動決定前に:

```text
if E < E_target and R > 0:
    reserveを使ってE_targetまで補充
```

```text
draw_R = min(R, (E_target-E)/reserve_mobilize_eff)
E += draw_R * reserve_mobilize_eff
R -= draw_R
loss = draw_R * (1-reserve_mobilize_eff)
```

lossは`energy_out_cum`。

夜・光・tick番号は一切参照しない。

# 7. starvation response / homeostasis

現在のEnergy state:

```text
e = clip(E / E_max, 0, 1)
```

遺伝子:

```text
s = genome[starvation_sensitivity]
```

Config:

```text
activity_floor = 0.10
```

活動係数:

```text
activity = activity_floor + (1-activity_floor) * e**s
```

性質:

```text
s=0 -> activity=1 常時
s>0 -> E低下でactivity低下
e=1 -> activity=1
e=0 -> activity=activity_floor
```

## 7.1 V1.9でactivityを掛ける対象

最小実装として:

```text
movement v_max
BMRのsize-scalable部分
repair budget
```

BMR:

```text
BMR = bmr_core
    + activity * (bmr_coef - bmr_core) * M^0.75
```

`bmr_core`は不可避maintenance floorとして残す。

movement:

```text
v_max_v19 = activity * v_max_v18
```

repair:

```text
repair_budget_v19 = activity * repair_budget_v18
```

V1.9では以下へactivityを掛けない:

- bmr_core
- membrane upkeep
- damage resistance upkeep
- resource uptake capacity

これにより飢餓時にも資源を取得する能力自体は消さず、無駄な運動/非core代謝を抑える。

# 8. reserve capacityのtrade-off

reserve_capacityを増やすとR_maxが増え、飢餓耐性が上がる。

一方、reproduction thresholdは`T_max`のfractionで判定するため、同じthreshold geneならreserve容量を増やすほど繁殖に必要なabsolute internal Energyも増える。

これを第一の自然なtrade-offとする。

V1.9初期実装ではreserve容量だけに人工的なfitness penaltyを追加しない。
storage/mobilization lossと繁殖遅延の帰結に任せる。

# 9. reproduction

世界定数`repro_energy_frac`を廃止し、遺伝子へ移す。

```text
T = E + R
T_max = E_max + R_max
theta = genome[reproduction_threshold]

Energy gate:
T >= theta * T_max
```

Matter gateは当面維持:

```text
matter >= repro_matter_frac * body_size
```

`birth_overhead`も維持。

## 9.1 birth overhead支払い

`spend_energy(org, amount)` helperを作り:

```text
1. operational Eから支払う
2. 不足時のみreserveをmobilizeして支払う
3. mobilization lossをledgerへ
4. 全internal Energyで払えなければ繁殖しない
```

## 9.2 childへのEnergy/Reserve分配

既存`reproduction_investment`を残す。

出生overhead後:

```text
f = genome[reproduction_investment]
e_child_offer = f * parent.E
r_child_offer = f * parent.R
```

childのmutated genome / child matterからE_max_child, R_max_childを求め、それぞれcapacityまで受け取る。

capacityを超えるoffer分は親へ残す。

親はmatter減少後にcapacityを再計算し、overflowがあれば:

```text
operational excess -> reserveへ移せる分は移す
残り -> heat
reserve excess -> heat
```

Energy ledgerを厳密に閉じる。

---

# 10. death / corpse

死亡時、corpseのrecoverable Energyは:

```text
corpse_energy = operational E + reserve R
```

とする。

reserveは特定のstorage polymerを意味せず、「死後に一部回収可能な内部化学自由エネルギー」のcoarse-grain。

死亡後の既存corpse energy decayへ統合する。

# 11. chemicalをH2-like substrateへ変更

V1.8の`world.chemical`はEnergy stockそのものだった。
V1.9では**基質量**へ意味を変更する。

推奨実装名:

```text
world.h2
world.h2_source_flux
```

Config:

```text
h2_vent_flux             = 16.0   # provisional substrate/tick/vent
h2_loss_frac             = 0.10
h2_uptake_coef           = 0.5
h2_uptake_half           = 1.5
h2_energy_yield          = 1.0    # E-equivalent/substrate
h2_conversion_efficiency = 0.60
```

旧Exp13の数値を科学的最終値として継承する意味ではない。
単位変更後のimplementation referenceであり、V1.9 baseline成立確認後に粗調整する。

## 11.1 uptake

```text
H(C,K)=C/(C+K)

J_raw = h2_uptake_coef
      * genome[chemical_absorption]
      * effective_surface(M)
      * phi
      * H(local_H2, h2_uptake_half)
```

`J_raw`はEnergyではなくH2-like substrate demand。

セル内競合はV1.4以降と同じ需要比例配分を使う。

取得substrate `J` から:

```text
chemical_free_energy = J * h2_energy_yield
usable_gain = chemical_free_energy * h2_conversion_efficiency
conversion_loss = chemical_free_energy - usable_gain
```

usable gainは`credit_energy()`へ渡す。
conversion lossはheat ledgerへ。

## 11.2 Energy ledger

H2 stockはEnergy-equivalentでledgerへ入れる。

```text
H2_energy_equiv = h2_stock * h2_energy_yield
```

外部source:

```text
energy_in += h2_source_amount * h2_energy_yield
```

環境loss:

```text
energy_out += lost_h2_amount * h2_energy_yield
```

これによりsubstrate→usable Energy変換後もworld Energy bookkeepingを閉じる。

# 14. zero能力からのmutation

V1.9では以下の初期値が厳密に0:

```text
light_absorption
predation_efficiency
(corpse_digestion: 人間判断次第)
```

初期jitterは乗算なので0のまま維持する。
standing phototrophyを最初から混ぜない。

繁殖時mutationのadditive項だけで0から立ち上げる。

現行`GENE_SCALE`の手指定小scaleを見直し、原則:

```text
GENE_SCALE = GENE_MAX - GENE_MIN
```

へ変更する案を採用する。

mutation式自体:

```text
child = parent * lognormal(...)
child += Normal(0, additive_mutation_frac * sigma * GENE_SCALE)
```

は維持する。

`additive_mutation_frac=0.01`は暫定維持。

これによりrange=5の能力geneではinitial mutation_rate=.05時:

```text
additive sigma = 0.01 * .05 * 5 = .0025
```

となり、現行lightの約.00025より一桁大きい。

実装前/直後に解析的または軽量Monte Carloで:

- 0 -> positive mutation waiting time
- 0 -> 生理的に意味ある値までの世代数

を確認する。

特定のlight geneだけへ特別bonus mutationは入れない。

# 20. conservation

`system_energy()`:

```text
sum(organism.energy)
+ sum(organism.reserve)
+ sum(corpse.energy)
+ world.H2_energy_equivalent
```

外部lightはstockではないので従来どおりsystem stockへ含めない。

Energy balance:

```text
initial + cumulative external energy in
- cumulative heat/loss out
= current system energy
```

含めるloss:

- maintenance/movement/repair
- birth overhead
- light overflow
- storage conversion
- reserve mobilization conversion
- H2 conversion inefficiency
- H2 environmental loss
- corpse decay

Matter ledgerはV1.9推奨案（CO2 implicit）なら現行を維持する。

# 25. 実装前に人間判断が必要な3点

## Q1. CO2をV1.9でexplicit fieldまで入れるか

推奨: **入れない。H2 explicit + CO2 implicit。**
理由: carbon matter ledgerまで同時に変えるとV1.9が大きくなりすぎる。

## Q2. initial iLUCAをvent/source habitatへ置くか

推奨: **置く。**
理由: chemical-first祖先を資源から無関係な世界全域へ撒く初期条件の方が人工的。

## Q3. corpse_digestionを初期0にするか

推奨: **0にする。**
理由: 現行能力はgeneric heterotrophyではなく具体的scavengingで、祖先に最初から与える根拠が弱い。

この3点が決まれば、V1.9世界ルールはSonnetへ実装指示可能なレベルまで固定できる。
