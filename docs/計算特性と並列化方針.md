# 計算特性と並列化方針 — クラウド環境選定のための分析

更新: 2026-08-29
測定: `tools/benchmark.py`（ローカルPC: Intel Core i7-14700F、物理20/論理28、Windows 11）

本書は「どこが遅いのか」「コアを増やせば速くなるのか」「並列化する価値があるのか」を
判断するためのデータと分析。**最適化そのものは目的にしていない。**

---

## 1. 結論（先に要約）

| 問い | 答え |
|---|---|
| ボトルネックは何か | **CPU。** それも近傍探索（接触判定＋行動判断）が約63% |
| メモリはボトルネックか | **いいえ。** 個体数1,900でも約50MB。桁違いに余裕 |
| 描画・I/Oはボトルネックか | **いいえ。** ヘッドレスでは描画ゼロ、記録I/Oは6〜11% |
| 現状はシングルコアか | **完全にシングルコア。** 全シナリオでCPU使用0.98コア |
| コアを増やせば速くなるか | **1 runは速くならない。複数runの同時実行なら速くなる** |
| 並列化の単位 | **run（seed）単位。** 実装済み（`run_batch.py --workers`） |
| クラウドで重視すべき点 | **シングルスレッド性能 × 物理コア数。** メモリ容量はほぼ不問 |

## 2. 単一プロセス性能（基準値）

描画・記録なし。個体数は「初期個体数＋ウォームアップtick数」を固定して決定的にしている。

| シナリオ | 個体数 | ms/step | step/s | CPU使用 | 最大RSS |
|---|---|---|---|---|---|
| light | 207 | 3.99 | 250.4 | 0.98コア | 43.8 MB |
| standard | 364 | 6.78 | 147.5 | 0.99コア | 45.3 MB |
| dense | 1,869 | 41.56 | 24.1 | 0.98コア | 49.8 MB |

**CPU使用が全シナリオで0.98〜0.99コア** = 完全にシングルスレッド。
NumPyは使っているが、配列が40×40と小さくSIMD/マルチスレッドの恩恵はほぼない。

### 個体数に対するコストの伸び

Exp03の実測（`performance.csv`、6 run分）。

| 個体数帯 | ms/tick中央値 | 個体あたり µs |
|---|---|---|
| 0–250 | 5.45 | 25.2 |
| 250–500 | 16.4 | 42.1 |
| 500–750 | 29.0 | 47.5 |
| 1,000–1,500 | 57.4 | 51.8 |
| 2,000–3,000 | 187 | 73.8 |
| 4,000–5,000 | 263 | 63.8 |

**個体あたりコストが密度とともに上昇する**（25 µs → 50〜74 µs）。
つまり全体はおよそ O(n^1.1〜1.2) で、単純な線形より悪い。
近傍セル内の個体数が増え、接触判定の走査対象が増えるためと考えられる。

長期・高密度の実験ほど不利になるので、実験計画時はこの非線形性を見込む必要がある。

（注: Exp03は14並列実行のため競合の影響を含む。絶対値ではなく傾向として読む）

| 項目 | 測定値 | 評価 |

| 描画（SDLダミードライバ、個体数251） | 1.50 ms/frame（描画のみ最大665 FPS） | ヘッドレス実験には無関係。GUIでも計算より軽い |

（測定を2回行い +6.4% と +10.6% だった。run間のばらつきがこの程度あることに注意）

**メモリは全シナリオで44〜50 MB。** 個体数が9倍になっても6MBしか増えない。
クラウドのメモリ容量は選定基準にならない。

## 5. 並列スケーリング（run単位）

同一負荷をNプロセス同時実行し、総スループットの伸びを測定。
各プロセスは独立したシミュレーションで、**プロセス間通信は一切ない**。

| 並列数 | 総step/s（計算のみ） | 倍率 | 効率 |
|---|---|---|---|
| 1 | 318 | 1.00x | 100% |
| 2 | 631 | 1.98x | 99% |
| 4 | 938 | 2.94x | 74% |
| 8 | 1,477 | 4.64x | 58% |
| 16 | 1,696 | 5.32x | 33% |
| 20 | 1,948 | 6.12x | 31% |
| 28 | 2,144 | 6.73x | 24% |

プロセス起動時間を含む「実測」値も併記しているが差は約4%。起動コストは支障にならない。

### この結果の読み方（重要）

**2並列で効率99%** は、この処理が本質的に embarrassingly parallel であることを示す。
同期・共有状態・IPCが一切ないので、原理的には物理コア数まで線形に伸びるはず。

にもかかわらず4並列以降で効率が落ちるのは、**測定機のCPUがハイブリッド構成**
（P-core 8個＋E-core 12個）で、E-coreがP-coreより大幅に遅いためと考えられる。
20を超える部分はハイパースレッディングなので効率低下は当然。

したがって **この数字はクラウドでのスケーリングを過小評価している可能性が高い。**
全コアが同性能のサーバCPU（EPYC / Xeon など）では、物理コア数近くまで
線形に近い伸びが期待できる。

作業セットは1プロセスあたり50MB、実際に毎tick触るデータは1MB未満なので、
メモリ帯域やキャッシュ競合が律速する可能性も低い。

**同じベンチマークをクラウド上で実行して確認すること。それが本ツールの目的。**

## 6. 並列化するならどの単位か

| 単位 | 評価 |
|---|---|
| **run（seed）単位** | **最適。実装済み**（`run_batch.py --workers`）。同期不要、効率99%（2並列時） |
| 条件（アブレーション）単位 | run単位と同じ。Exp04のように4条件×20 seed = 80 runを分散できる |
| tick内の個体ループ | **勧めない。** 決定性が壊れる。個体は逐次処理を前提に相互作用しており、並列化には設計変更が必要 |
| 空間分割（領域ごとに並列） | **勧めない。** 境界処理で決定性と保存則が壊れやすい。効果に対して複雑さが大きすぎる |

設計原則6「決定性を壊さない」があるため、**1 run内の並列化は採用しない**。
run単位の並列で十分な速度が得られており、そちらを伸ばすのが合理的。

### 1 runを速くしたい場合の選択肢（現時点では不要）

長期実験1本を速くしたい場合のみ検討する。優先順位は:

1. 近傍探索の改善（接触判定38%が対象。セルサイズの調整や早期棄却）
2. Numba / Cython による近傍探索のコンパイル（結果が変わらないか要検証）
3. Rust / C++ 拡張

いずれも `tools/verify_vs_ref.py` で**結果が1ビットも変わらないこと**を
検証しながら進める必要がある。

## 7. クラウド環境選定で重視すべきスペック

| 優先度 | 項目 | 理由 |
|---|---|---|
| **1** | **シングルスレッド性能**（クロック × IPC） | 1 runの速度を直接決める。1 runは1コアしか使えない |
| **2** | **物理コア数**（vCPUではなく） | 同時実行できるrun数を決める。ハイパースレッディングの効きは薄い |
| **3** | 全コアが同性能であること | ハイブリッド構成は遅いコアが足を引っ張る |
| 4 | 持続クロック（サーマルスロットリング耐性） | 数時間の連続実行が前提 |
| — | メモリ容量 | **ほぼ不問。** 1 runあたり50MB。28並列でも1.5GB程度 |
| — | GPU | **不要。** GPU向きの処理は一切ない |
| — | ストレージ性能 | ほぼ不問。記録I/Oは全体の6〜11%、書き込み量も小さい |

### 具体的な目安

- Exp04規模（4条件 × 20 seed × 40,000 tick = 80 run）の所要時間は
  **シングルスレッド性能と物理コア数の積**でほぼ決まる
- 「vCPU 64個」より「物理16コアで高クロック」の方が速い可能性がある。
  共有vCPUインスタンスはノイジーネイバーの影響も受ける
- **選定候補を絞ったら、各候補で `tools/benchmark.py --full` を実行して比較する。**
  カタログスペックより実測が確実

## 7.5 GitHub Actions 実測結果 (2026-08-29)

`benchmarks/gh-actions-ubuntu-2core.json`。ワークフロー: `.github/workflows/benchmark.yml`

### ランナーのスペック

| 項目 | 値 |
|---|---|
| CPU | Intel Xeon Platinum 8370C @ 2.80GHz |
| コア | **物理 1 / 論理 2 (ハイパースレッド)** |
| メモリ | 7.8 GB |
| Python | 3.12.3 / NumPy 2.5.2 |

### 単一プロセス性能 (ローカル比)

| シナリオ | ローカル step/s | Actions step/s | 比 |
|---|---|---|---|
| light | 250.4 | 125.7 | **0.50x** |
| standard | 147.5 | 76.9 | **0.52x** |
| dense | 24.1 | 13.3 | **0.55x** |

1 runあたり **ローカルの約半分の速度**。Xeon 8370C の 2.8GHz に対し
i7-14700F の P-core は最大5GHz超なので妥当な差。

### 並列スケーリング: 実質ゼロ

| 並列数 | 総step/s | 倍率 | 効率 |
|---|---|---|---|
| 1 | 153 | 1.00x | 100% |
| 2 | 155 | **1.01x** | 51% |
| 4 | 147 | 0.97x | 24% |

**物理1コアなので並列化の効果がない。** 2並列にしても1%しか増えない
(ハイパースレッドはCPUバウンドな本処理には効かない)。4並列では逆に遅くなる。

ローカルが28並列で6.73倍に伸びたのとは対照的で、
**1ジョブあたりのバッチ処理能力はローカルの約1/14** (153 vs 2,144 step/s)。

### 記録I/Oと処理内訳

- 記録I/O: **+0.8%** (ローカルは+6.4〜10.6%)。Linuxの方が書き込みが軽い
- フェーズ内訳はローカルとほぼ同一 (行動判断25.5% / 捕食20.3% / 死骸摂取16.7%)。
  **処理特性は環境によらない**

### 運用判断: ジョブ並列なら速度は足りるが、無料枠の分数が足りない

1ジョブは遅いが、**Actionsはmatrixで複数ジョブを同時実行できる**。
Freeプランの同時実行上限は20ジョブなので:

```
20ジョブ × 153 step/s = 約3,060 step/s
```

これは**ローカルPCの28並列 (2,144 step/s) を上回る**。速度自体は問題にならない。

問題は**消費分数**である。Privateリポジトリでは無料枠が月2,000分。

Exp04規模 (4条件 × 20 seed × 40,000 tick = 80 run) の見積もり:

| 項目 | 値 |
|---|---|
| 1 runの所要 (Actions) | 約28〜38分 |
| 80 runの合計 | **約2,200〜2,650分** |
| Free無料枠 | 2,000分/月 |
| 実時間 (20ジョブ並列) | 約2.2時間 |

**Exp04 1回で月間無料枠を超える。** 実時間は短いが分数が持たない。

### 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **リポジトリをPublicにする** | **Actions分数が無制限無料になる。** 最も効果が大きい。公開してよいかはプロジェクト側の判断 |
| B | 重いバッチはローカル、Actionsは軽い検証とCIに使う | 追加費用ゼロ。現状の運用の延長 |
| C | 実験規模を縮小 (seed数やtick数を減らす) | 統計的検出力が落ちる |
| D | GitHub Pro (月3,000分) や従量課金 | 有料。今回は対象外 |

**推奨は A か B。** 研究用途で公開に支障がなければ A が圧倒的に有利。
公開したくない場合は B とし、Actions は CI と短時間の検証に限定する。

なお無料枠を使い切っても、GitHubの既定の支出上限は $0 なので
**自動的に課金されることはない** (実行がブロックされるだけ)。

### GitHub Codespaces について

開発環境としては問題ないが、**本番の長時間計算には向かない**。

- 標準は2コア。Actionsランナー (物理1コア) と同等かやや上程度と見込まれる
- コンテナのCPU制限があるため、`benchmark.py` は cgroup の割当も記録する
- まず `--quick` で疎通確認し、`--full` で実測値を取ってから判断すること
