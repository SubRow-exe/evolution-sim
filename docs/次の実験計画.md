### 分かったこと

| 事実 | 根拠 |
|---|---|
| 適応度関数なしで方向性選択が発生する | exp01 (光利用能力 0.30→0.445) |

### 未解決の問い

1. **転移はどのくらいの確率・時期で起こるのか** (5 seedでは統計不足) → Exp03 / Issue #3
2. **転移の必要条件は何か** (どの遺伝子の可変性が引き金か) → Exp04 / Issue #4
3. **転移後どうなるのか** (高mutation_rate 0.203 は維持されるか、低下に転じるか) → Exp05 / Issue #5

5. **各遺伝子の初期値近傍で利益・コストが連続的か** (進化経路が実装都合で塞がれていないか) → Exp07 / Issue #16

### 計算性能 (2026-08-28)

結果を変えない実装最適化により **1.4倍** 高速化済み (低密度1.39x / 高密度1.44x)。
`tools/golden.py` と `tests/test_golden.py` が結果不変性をCIで恒久的に保証する。

実測 (i7-14700F, 20物理コア/28論理スレッド):

| 個体数 | 最適化前 | 最適化後 |
|---|---|---|
| 400 | 9.18 ms/tick | 6.59 ms/tick |
| 1,852 | 53.83 ms/tick | 37.44 ms/tick |

**`--workers` は 14 を推奨** (従来の計画にあった 5 は過小)。

### ⚠ 結果はOSに依存する (2026-08-28 判明)

同じseed・同じconfigでも、**WindowsとLinuxでは結果が異なる**。

原因は `math.sin` / `cos` / `atan2` / `hypot` と `** 0.75` (pow) が
各OSのlibm実装であり、最終ビットが一致しないため。numpyはlockで固定済みなので
バージョン差ではない。

したがって:

- **実験は同一マシンで実行し、`meta.json` のプラットフォームを確認すること**
- 異なるOSで実行した結果を直接比較してはいけない
- `tools/golden.py` の指紋は `os-machine` をキーに保存される
- OSを跨いだ実装の等価性検証は `tools/verify_vs_ref.py` が行う
  (定数比較ではなく、同一マシン上で2つの実装を実際に走らせて比較する)

これは設計原則7「同じSeedで完全再現できるか」の適用範囲を
**「同一プラットフォーム内で」** と限定する必要があることを意味する。

## 2. 次の実験 (優先度順)

### Exp 03: 転移の発生率と時期の分布 ★最優先

**問い**: 転移は何%のseedで、いつ起こるのか。

```bash
uv run python tools/run_batch.py --seeds 1-20 --ticks 40000 --workers 14
```

見込み所要時間 約30分 (高速化1.4倍 + workers 14 による。従来見積は約1.6時間)。

- 40,000 tickまで延ばす (exp02では30,000で未転移のseedが残った)
- seed 1〜5 は exp02 と同一条件のため、最初の30,000 tickが完全一致するはず。
  **再現性の検証を兼ねる**

**記録すること**: 転移した seed の割合、転移tickのヒストグラム、
転移seedと非転移seedの最終遺伝子分布の比較。

### 重要: これは「打ち切りデータ」である

40,000 tickで測れるのは転移率そのものではなく、**「40,000 tickまでに転移した割合」**
である。未転移seedが後で転移する可能性を排除できない (exp02のseed 5は30,000 tick時点で
light_absorption 0.88 と上昇途中だった)。

したがって単一の「転移率◯%」という数字で報告してはいけない。

- **累積発生率曲線** (横軸tick / 縦軸それまでに転移した割合) として報告する
- 未転移seedについても light_absorption と body_size の**軌跡**を記録し、
  「転移しない」のか「まだ転移していないだけ」なのかを区別する

**判定**: 累積発生率曲線が特定tick帯で立ち上がり、その後平坦になるなら閾値型・
蓄積型の可能性が高い。曲線が最後まで直線的に増え続けるなら、一定確率で
偶発的に起こる事象 (待ち時間分布) に近い。

### Exp 04: アブレーション実験 (改善方針 §3)

**問い**: 転移に必要な遺伝子の可変性はどれか。

**前提**: Exp03 で baseline の累積発生率が判明していること。これが比較対象になる。

### 単一seedでは結論が出ない (2026-08-28 修正)

当初は「転移が明確な seed 4 で1条件1回ずつ実行する」設計だったが、これでは判定できない。

転移は baseline でも一部のseedでしか起きない (exp02では5分の2)。仮に転移率が40%なら、
`body_size` を固定して転移が起きなくても、**その遺伝子が転移と無関係でも約60%の確率で
同じ結果になる**。「転移しなかった」という観測は、単独では何の証拠にもならない。

判定は非対称である。

| 観測 | 結論 |
|---|---|
| 固定しても転移が**起きた** | その遺伝子は必要条件では**ない** (1例で反証成立) |
| 固定したら転移が**起きなかった** | **単独では結論不可**。複数seedで発生率を比較する必要がある |

### 修正後の設計

各条件について **Exp03と同じseed集合 (1〜20)** で実行し、baseline の累積発生率と比較する。

```bash
for G in body_size reproduction_investment mutation_rate light_absorption; do
  uv run python tools/run_batch.py --seeds 1-20 --ticks 40000 --workers 14     --fix-genes $G --out runs/exp04_fix_$G
done
```

**未実装**: `tools/run_batch.py` に `--fix-genes` を通す口がない (T5)。

**判定**: baseline の累積発生率曲線と各条件の曲線を比較する。
発生率が有意に下がる (例: 40% → 0〜5%) 遺伝子が必要条件の候補。
seed 20件では検出力が限られるため、**差が小さい場合は「不明」と報告し、
seedを増やすか別の切り口を検討する**。無理に結論を出さない。

### `--fix-genes` の性質と限界

固定遺伝子は初期ばらつきも与えられないため、全個体・全世代で完全に一定となる。
乱数も固定遺伝子の分だけ消費するので、**変異呼び出しごとの乱数消費数は通常実行と一致する**。

ただし「1遺伝子以外は同一の世界」にはならない。最初の分岐以降は生存・繁殖する個体が
変わり、繁殖イベント数自体が変化するため、世界の歴史は不可避的に発散する。
これは実装の不備ではなく、確率過程の性質である。だからこそ複数seedでの比較が必要になる。

### Exp 05: 転移後の長期挙動

**問い**: ヒッチハイクで上がった mutation_rate (0.203) はその後どうなるか。

```bash
uv run python main.py --headless --ticks 150000 --seed 4
```

高い突然変異率は有害変異も増やすため、一掃が終わって集団が均一化した後は
不利に転じて低下する可能性がある。これが観察できれば
**「ヒッチハイクで上昇 → 選択で低下」という二段階の現象**を捉えたことになる。

**注意**: 個体数3,600規模で15万tickは長時間。`max_population_halt` (既定20,000) に
達した場合は自動保存して停止する。Ctrl+Cでも途中結果は完全に出力される。

### Exp 06: 災害の影響 (仕様書 Experiment 4)

**問い**: 転移直前・転移直後に大量絶滅が起きると何が変わるか。

一掃が進行中の集団に災害を与えると、遺伝的浮動で転移が潰れる可能性がある。

**実装済み** — `--disaster-at` で指定tickに災害を起こせる (カンマ区切りで複数可)。

```bash
uv run python main.py --headless --ticks 40000 --seed 4 --disaster-at 25000
uv run python main.py --headless --ticks 40000 --seed 4 --disaster-at 20000,25000,30000
```

seed 4 の転移は約25,400 tickなので、その直前・最中・直後で結果がどう変わるかを比較する。

### Exp 07: 14遺伝子の局所感度解析 (Issue #16 / `V1_モデル校正方針.md`)

**問い**: 各遺伝子は初期値の近傍で、増減が連続的に利益・不利益へつながるか。
進化経路が実装都合で塞がれている遺伝子はないか。

各遺伝子の初期値を単独で ±10% / ±20% 変えて短〜中期の複数seed実行を行う。

**⚠ 現状では実行できない**: 初期遺伝子値は `evosim/genome.py` の `INITIAL_GENOME`
というモジュール定数であり、Configから変更する手段がない。`--fix-genes` は
「初期値で固定」はできるが「初期値そのものを変える」ことはできない。
先に T6 の実装が必要。

**規模に注意**: 14遺伝子 × 4水準 × N seed。N=5 なら 280 run になる。
tick数を明示して設計すること。局所感度の測定が目的なので、
転移が起きる前の短期 (5,000〜10,000 tick程度) で十分な可能性が高い。
**先に1遺伝子で予備実験を行い、必要tick数と検出力を確かめてから全遺伝子へ広げる。**

**特に疑う点** (`V1_モデル校正方針.md` より):
- `light_absorption` の微増が他能力より過度に有利ではないか
- `predation_efficiency` の初期近傍が「コストだけ増えて利益ゼロ」の谷になっていないか
- `body_size` 小型化が繁殖条件と維持費の両方から二重に有利になっていないか

**原則**: この結果を見て「多様性を増やすために数値を調整」しない。
目的は進化空間の断絶・不連続の可視化である。

## 4. 進め方のルール

1. **1実験につき1条件のみ変更する。** 複数変えると原因が特定できない
2. 結果は `experiments/expNN_<名前>/` に `NOTES.md` 付きで保存する
   (`events.csv` と `snapshots/` は容量次第で除外可。seedがあれば再現できる)
3. **baseline (`v1.1-baseline`) の挙動を変える変更は、実験が一段落するまで入れない**
4. 変更を入れたら `uv run pytest tests` を全通しする (CIでも自動実行)
5. 本書の「現在地」と「次の実験」を更新してからPRを出す
6. **結論が出ないときは「不明」と書く。** 検出力が足りない観測から
   無理に結論を出さない (下記 6.1 参照)

## 6. 改訂の理由 (2026-08-28)

レビューで見つかった問題と、それに対する修正の記録。

### 6.1 Exp04 は単一seedでは結論が出ない (最重要)

**問題**: 当初設計は「転移が明確な seed 4 で1条件1回ずつ実行」だったが、
転移は baseline でも一部のseedでしか起きない確率的事象である。
1回の実行で「転移しなかった」ことは、その遺伝子が原因である証拠にならない。
転移率40%なら、無関係な遺伝子を固定しても60%の確率で同じ結果が出る。

**修正**: Exp03 と同じseed集合で複数実行し、累積発生率を baseline と比較する設計へ変更。
判定が非対称であること (転移が起きれば1例で反証成立、起きない場合は複数必要) を明記した。

**波及**: `run_batch.py` に `--fix-genes` を通す口が必要 (T5)。

### 6.2 Exp03 の測定値は打ち切りデータである

**問題**: 「40,000 tickまでに転移した割合」を「転移率」と書くと、
未転移seedが後で転移する可能性を無視することになる。
exp02 の seed 5 は 30,000 tick 時点で light_absorption が上昇途中だった。

**修正**: 単一の割合ではなく累積発生率曲線として報告する設計へ変更。
未転移seedの軌跡も記録し、「転移しない」と「まだ転移していない」を区別する。

### 6.3 Exp07 は前提機能が存在せず実行できない

**問題**: Issue #16 は遺伝子の初期値を ±10/20% 変える設計だが、
`INITIAL_GENOME` は `evosim/genome.py` のモジュール定数で、Configから変更できない。
また 14遺伝子 × 4水準 × N seed の規模が明示されておらず、tick数次第で爆発する。

**修正**: 前提機能を T6 として実装タスクに登録し、規模と予備実験の必要性を明記した。

### 6.4 `--workers 5` は過小だった

**問題**: 実行環境は 20物理コア / 28論理スレッド (i7-14700F) であり、5は使い切れていない。

**修正**: 推奨値を 14 に変更。あわせて結果を変えない実装最適化で 1.4倍 高速化した
(`tools/golden.py` で結果不変性を機械的に保証)。Exp03 の見込みは約1.6時間から約30分になった。

### 6.5 ドキュメント間の不整合

**問題**: 本書は README と AGENTS.md から「最初に読め」と指定されているが、
後から追加された Exp07 (Issue #16) と Issue #17 が記載されておらず、
`V1_モデル校正方針.md` の「Exp03〜Exp07」という記述と食い違っていた。

**修正**: Exp07 を追加し、実行順序と Issue 番号の対応を明記した。
