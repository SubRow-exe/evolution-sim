## 1. 目的

Exp10正式結果でV1.6 temporal biased random walkは採用された。一方、進化OFF実装漏れ中のexploratory B1では、移動可能になった世界で `body_size` が約1.0から約0.226へ縮小し、populationが約6,500まで増えた。

これはExp10正式結果ではないが、現行世界に強い小型化選択圧が存在する可能性と、同じ総Matterが多数の小型個体へ分割されることで計算量が急増する設計課題を示した。

V1.7ではbody_size下限を上げたり、populationを強制削減したりせず、**生命1個体として存在するために縮小しきれない基礎維持代謝**を世界側の共通生理ルールとして導入する。

目標は特定サイズを正解として与えることではない。

> 小型ほど無条件に有利という一方向性を崩し、小型・大型それぞれに自然な得失が生じ、環境ごとに異なるbody sizeが選択されうる余地を作る。

---

## 2. LUCA-inspiredな位置づけ

`docs/LUCA参照モデル方針.md` に従う。LUCAそのものは再現しない。

現実から借りるのは、最小クラスの細胞でもmaintenance metabolism / basal power requirementがゼロへ消えず、小型化すると総代謝に占める維持負担が相対的に大きくなる、という**構造・因果**である。

Energy/tickをJoule/secへ直接校正せず、LUCAらしさへ適応度を与えない。祖先側に生理的根拠を置いた後の進化結果は自然選択へ任せる。

参考:
- Kempes et al. (2017), *Drivers of Bacterial Maintenance and Minimal Energy Requirements*, Frontiers in Microbiology 8:31.
- LaRowe & Amend (2015), *Power limits for microbial life*, Frontiers in Microbiology 6:718.
- Moody et al. (2024), *The nature of the last universal common ancestor and its impact on the early Earth system*, Nature Ecology & Evolution 8:1654–1666.

## 3. 現行モデルの小型化圧

現行世界にはすでに完全なサイズ比例ではないコストがある。

- `sense_upkeep * sensory_range^2` はサイズ非依存
- `birth_overhead=2.0 E` は繁殖1回ごとの固定費
- 通常wanderでは `v ∝ M^-1/2` なので `move_cost * M * v^2 / efficiency` は固定形質・健全時にサイズ非依存

それでもexploratory runでは極端な小型化が生じた。

小型側には少なくとも:

- 有効表面積 `M^(2/3)` による高い単位Matterあたり交換能力
- 繁殖に必要なEnergy/Matterが小さいことによる短い世代時間
- `v_max ∝ M^-1/2` による高速移動

という利点が残る。

V1.7はこれらを削除せず、生命維持費の縮小不能部分を追加することで対抗する。

## 4. 採用する式

現行:

```text
BMR_old = bmr_coef * M^0.75
bmr_coef = 0.3
```

V1.7:

```text
BMR_new = bmr_core + (bmr_coef - bmr_core) * M^0.75
0 <= bmr_core <= bmr_coef
```

- `M`: 現在の身体Matter (`org.matter`)
- `bmr_core`: 個体ごとの縮小不能なcore BMR `[E/tick/individual]`
- `bmr_coef=0.3`: `M=1` における基準BMR

コード・Config・実験表記は **`bmr_core` に統一する**。概念説明で「core maintenance」と呼んでも、別名パラメータを作らない。

### 4.1 性質

```text
bmr_core=0   -> V1.6と完全一致
M=1          -> 任意の合法bmr_coreでBMR=0.3
M->0         -> BMRはbmr_coreへ近づく
bmr_core=0.3 -> BMR=0.3でサイズ非依存
```

### 4.2 大型側への影響は意図的

この式は「小型へ固定費を足す」だけではない。`M>1`ではV1.6よりサイズ依存部分が小さくなるため、**大型側のBMRも相対的に低下する**。

これは隠れた副作用ではなく、`M=1`の基準BMRを変えずに既存BMRを「core + scalable」に再解釈した結果として意図的に受け入れる。

したがってV1.7は、

- 小型: coreを少ないMatterで負担する
- 大型: coreを大きな身体で償却できる

というトレードオフを新しく作る。

### 4.3 純加算形を採らない理由

代替として以下も検討した。

```text
BMR_additive = bmr_coef * M^0.75 + bmr_core
```

利点:
- V1.6との差分が「固定費の追加」だけで分かりやすい
- 大型の既存BMRを下げない

不採用理由:
- `M=1` のreference organismの総BMR自体を `0.3+bmr_core` へ引き上げる
- 「既存BMRのうち縮小不能な部分を切り分ける」というLUCA-inspiredな解釈ではなく、世界全体の代謝基準を上乗せ変更する
- `bmr_core` の校正と同時にreference BMR総量まで変更することになる

よって、**M=1の既存アンカー0.3を維持し、内訳を再配分する現行式を採用する。**

ただし `M=1` の不変性は1点だけであり、正式runの `initial_matter=0.8` では `bmr_core>0` により初期BMRが増える。これは隠さずPhase Aで監査し、初期絶滅等の解釈に使う。

## 5. V1.7で変更しないもの

- body_size遺伝子範囲 `0.2..10.0`
- 有効表面積 `M^(2/3)`
- Energy / Damage capacity
- 移動速度・移動費
- organ / sense / membrane / resistance upkeep
- reproduction threshold / child_matter_frac / birth_overhead
- light / chemical / nutrient吸収則
- V1.6 temporal biased random walk
- temperature / heat loss
- predation / defense
- 新規遺伝子
- populationを生態的に制御する処理

`bmr_core` は**遺伝子にしない**。当面は細胞生命に共通する生理ルールとする。

## 6. 実装仕様

Config:

```python
bmr_coef: float = 0.3
bmr_core: float = 0.0
```

実装:

```python
bmr = cfg.bmr_core + (cfg.bmr_coef - cfg.bmr_core) * s ** 0.75
```

入力時またはSimulation初期化時に:

```text
0 <= bmr_core <= bmr_coef
```

を検証し、違反は `ValueError`。

Energy台帳では従来BMRと同じ散逸Energyとして扱う。

Exp11選定前の通常defaultは `bmr_core=0.0`。Exp11で恒久値が選定された場合のみ別commitでdefaultへ反映する。

### 6.1 Config silent-drop対策

V1.7 Configを古いコードで読み、未知の `bmr_core` が黙って無視される事故を防ぐ。

実装時に必ず:

- 非ゼロ `bmr_core` のJSON round-trip test
- 保存configへの `bmr_core` 記録
- run summary / fingerprint / collect tableへの記録
- Exp11全45 Configで「生成JSON値 == ロード後Config値」のchecker

を追加する。

## 8. 必須テスト

1. `bmr_core=0` でV1.6完全一致
2. `M=1` で任意の合法値に対してBMR=`bmr_coef`
3. `bmr_core=bmr_coef` でBMRサイズ非依存

## 9. 小型化抑制原則との整合

過去方針の

> 小型化を抑えるためだけの人工的ペナルティは入れない

は維持する。

V1.7は「body_sizeが小さいから罰点を与える」ルールではない。微生物のmaintenanceに基づく**全個体共通の一般生理則**を導入し、その結果としてbody sizeの得失が変わるものである。

`max_population_halt`も生態ルールではなく正式runの計算安全装置であり、個体を殺したり繁殖を抑えたりしない。
