# 0. 総評とサマリ

## 0.1 総評

**V1.8の設計思想は正しい。** 「light型を弱く、chemical型を強く」という適応度補正を入れず、
環境場の時間構造と濃度依存吸収だけで生態的非対称を作るという方針は、絶対原則8・12に忠実で、
`docs/LUCA参照モデル方針.md` の「構造・因果・scalingを借り、絶対値は移植しない」とも整合する。

チェックリストと実行順の作り込みも、Exp11・Exp12で踏んだ失敗を確実に制度化している。

**しかし、実装前に必ず直すべき問題が6件ある。うち4件は数値検算で確認した。**

最も重いのは次の2点である。

> **(A) 昼夜cycleは「周期性」だけでなく「総light energyの3.14分の1化」を同時に導入している。**
> half-sine × `day_fraction=0.5` のperiod平均daylight factorは `0.5 × 2/π = 0.3183`。
> これは絶対原則9（原則1軸ずつ）に反し、かつ事前登録されたrescue ladderの上限
> `light_max=2.4` はenergy中立値 `3.77` に届かない。
>
> **(B) Exp13は全Phaseで `body_size=1.0` 固定だが、Exp12が確定した `bmr_core=0.15` 下の
> 平衡body_sizeは 0.2459 である。** 100 tickの夜を越せるのは `M≳0.33`。`M=0.246` は
> 83.8 tickで餓死する。**つまりExp13は、この世界が実際に生むサイズでV1.8を検証していない。**

これらを直さないままdispatchすると、Exp13は「A1がほぼ空振りでPASSし、
その値が恒久defaultになる」か「LIGHT_CALIBRATION_FAILで停止して何も決まらない」の
どちらかになる可能性が高い。

# 3. V1.8 物理設計のレビュー

## 3-1. M-1: 昼夜cycleが総light energyを3.14分の1にしている

### 事実

`daylight_factor` は `day_fraction=0.5` の half-sine である。period平均は解析的に求まる。

```text
period平均 daylight_factor
 = day_fraction × (1/π)∫₀^π sin θ dθ
 = 0.5 × (2/π)
 = 0.31831
```

つまり **V1.8のlight worldは、V1.7に対して総light energyが 31.8%（3.14分の1）になる。**

### なぜこれが問題か

V1.8仕様 §1 が狙うのは:

```text
light = 空間的に広い / 1地点1tickのfluxが薄い / 周期的
```

である。このうち「1地点1tickのfluxが薄い」は**濃度依存吸収 `H(I, K)` が担当**し、
「周期的」は**cycleが担当**するはずだった。

ところが現在のcycle実装は、周期性に加えて**総量を1/3にする**という第3の変更を同時に入れている。
これは絶対原則9「原則1軸ずつ変更する」に反する。

さらに実務上の帰結として、Exp13 A1が測る「light specialistが周期環境で成立するか」は、
**周期性の効果と総量1/3の効果を分離できない。** A1がFAILしたとき、
それが「昼夜という時間構造のせい」なのか「単にエネルギーが1/3になったせい」なのか判別できない。

### 変更提案（MUST FIX）

**cycleをenergy中立に正規化する。** 実装は1行で済む。

```text
案A（推奨）: factorを正規化する
  daylight_factor(tick) = sin(π u) / mean_factor      (phase < day_fraction)
                        = 0                            (それ以外)
  ただし mean_factor = day_fraction × 2/π = 0.31831

  -> peak factor は 1/0.31831 = 3.14
  -> period積分は enabled/disabled で厳密に一致
  -> 「昼は静的時の3.14倍明るく、夜は0」という、
     総量を変えずに時間構造だけを変えた世界になる

案B: light_max 側で吸収する
  light_max を 1.2 -> 3.77 (= 1.2 / 0.31831) にして cycle を入れる
  -> 効果は案Aと同じだが、light_max の意味が
     「静的peak」から「昼のpeak」へ変わるので文書の書き換えが増える
```

案Aなら `light_cycle_enabled=False` との総量一致が定義上保証され、
§10.2 のテストに「period積分が enabled/disabled で一致」という強い不変条件を追加できる。

**この変更を入れると M-3（rescue ladder）の問題も同時に消える。**
energy中立なら `light_max=1.2` のまま出発でき、ladderは
「周期性そのものが厳しすぎる場合の救済」という本来の役割に戻る。

### 副次的な注意

案Aを採ると昼のpeak flux は 1.2 × 3.14 = 3.77 になる。
`light_uptake_half=0.6` に対して `H(3.77, 0.6) = 0.863` となり、
昼のピークでは飽和に近い。これは意図どおり（明るい時間に効率よく取る）だが、
`light_uptake_half` の位置づけは「静的peakの半分」ではなくなるので、
根拠の記述を更新する必要がある。

## 3-2. S-1: `chemical_uptake_half=6.15` は存在しない状態を基準にしている

仕様 §3.2 の根拠は「現行標準vent生物不在stock約 `12.3` の1/2」である。

しかし `12.3` は**生物が1個体もいない場合の平衡stock**であり、
実際に個体がventに乗っている状態のstockではない。

`AGENTS.md` に記録されているExp09の残論点は:

```text
chemical_stimulus_half=12.3 と実測感知stock (0.02〜1.52) の1〜3桁の乖離
```

である。この実測帯に `H(C, 6.15)` を当てると:

| C | 状況 | `H(C, 6.15)` | 吸収の倍率 |
|---:|---|---:|---|
| 12.30 | 生物不在平衡 | 0.667 | 1.5分の1 |
| 1.52 | Exp09実測 上端 | 0.198 | **5.0分の1** |
| 0.50 | — | 0.075 | 13.3分の1 |
| 0.02 | Exp09実測 下端 | 0.0032 | **309分の1** |

つまり `H` は、**chemicalの瞬間収益を上げるどころか5〜300倍絞る方向に働く**可能性がある。
V1.8 §1 が狙う「見つければ高い瞬間Energy獲得速度」とは逆である。

### 緩和する要因（正直に併記する）

これは自己修正的でもある。吸収が絞られれば消費が減り、
`source − loss − 消費` の平衡stockは V1.7 より**高く**なる。
したがって実際の運転点は 0.02〜1.52 より上へ移動する。定性的には:

```text
V1.8 の vent 平衡 stock > V1.7 の vent 平衡 stock
```

なので、5〜300分の1という数字はそのまま実現しない。

### それでも問題である理由

**Exp13には `chemical_uptake_half` を校正する手段が一切ない。** 候補格子があるのは
`chem_uptake`（1.0 / 2.0 / 4.0）だけで、half は `6.15` 固定である。

`chem_uptake` は掛け算なので**burstの大きさ**は動かせるが、
**depletion応答の形（どのstock帯で効き始めるか）は動かせない。**
half が運転点から2桁ずれていると、`H` はほぼ線形領域（`H ≈ C/K`）でしか使われず、
「飽和して頭打ちになる」という設計意図が実現しない。

### 変更提案（SHOULD FIX）

いずれか。

```text
案1（安価・推奨）
  Exp13 Phase A に「A2-0: vent平衡stockの決定論/短期実測」を追加する。
  selected chem_uptake 候補ごとに、feature ON で 2,000 tick の
  vent cell stock 中央値を測り、chemical_uptake_half を
  その実測運転点の 1/2 として事前登録規則で決める。
  (chem_uptake と half の 2軸選定になるが、half は測定から導出されるので
   結果を見た後付け調整ではない)

案2
  chemical_uptake_half にも候補格子を置く (例: 0.5 / 1.5 / 6.15)。
  ただし A2 の run 数が 3倍になる。

案3（最小）
  6.15 のまま走らせるが、A2 の観測に
  「H(C) の実現値分布」を必須列として加え、
  H が常に 0.1 未満なら CHEMICAL_CALIBRATION_FAIL の理由として
  「half が運転点から外れている」と機械的に判別できるようにする。
```

案1が最も情報効率が良い。**いずれにせよ「半飽和定数を、その資源が実際に取る濃度帯から
決める」という原則を仕様へ明記すべき**である。V1.5の `chemical_stimulus_half=12.3` で
すでに同じずれが起きており、同じ間違いを吸収側で繰り返すことになる。

## 3-3. その他の物理設計は妥当

以下は現行実装と突き合わせて確認し、問題を見つけなかった。

- **route-specific penaltyを入れない判断（§4.1）は正しい。** 現行 `organ_upkeep` は
  `0.05 × matter × Σ(5能力)` で、`light_absorption` も `chemical_absorption` も
  対称に課金されている。ここに片側だけの項を足すのは絶対原則8違反になる
- **「植物は動かない」を実装しない判断（§4.2）も正しい。**
  移動費 `move_cost × M × v² / eff` は wander速度 `v ∝ 1/√M` を代入すると
  `M` が厳密に消えてサイズ非依存になるので、低収益環境では移動が相対的に高くつく。
  結果として低活動が選ばれる余地は既存機構だけで存在する
- **lightをstockにしない判断（§3.3）は物理的に正しい。** 光は到達したtickに使わなければ
  失われるflowであり、現行 `_absorb_light` も未利用分をどこにも積まない（`energy_in_cum` は
  実吸収分のみ加算）。台帳はこの点で既に正しい
- **vent sourceに有限寿命を入れない判断（§3.4）**も、V1.8のスコープ限定として妥当

## 4-4. M-5: `BURST_RATIO` の測定窓が非対称

Exp13 §5 の定義:

```text
LIGHT_DAY_GAIN  = median(route_gain_per_org_tick)
                  A1条件の daylight interval のみ / 時間窓の指定なし = 全10,000 tick
CHEM_BURST_GAIN = median(route_gain_per_org_tick)
                  vent placement の 最初の1,000 tick のみ
BURST_RATIO     = CHEM_BURST_GAIN / LIGHT_DAY_GAIN
```

問題は2つある。

### (a) 窓が違う

chemicalは**初期transient**（vent上に100個体を置き、stockは生物不在平衡 `C_eq=12.3` から開始）、
lightは**ほぼ平衡状態を含む全区間**である。比較になっていない。

### (b) 平衡状態の per-org-tick gain は係数にほとんど依存しない

人口が平衡に達すると、定義上

```text
1個体あたりの獲得 ≈ 1個体あたりの支出（維持費 + 繁殖投資の償却）
```

に張り付く。取り込み係数を上げても、上がるのは**個体数**（または資源の枯渇度）であって
**per-capita gain ではない。**

したがって `LIGHT_DAY_GAIN` は `light_max` にも `light_uptake_coef` にもほとんど依存せず、
おおよそ `maintenance / duty_factor` へ収束する。
`BURST_RATIO` が実際に測っているのは
**「chemicalの初期transient vs lightの平衡値」** であり、
`chem_uptake` の選定に使うには不適切である。

### 変更提案（MUST FIX）

```text
案A（推奨）: 窓を揃える
  LIGHT_DAY_GAIN も「最初の1,000 tick の daylight interval」から取る。
  両方とも初期transientで測るので、
  「初期条件を揃えたときの瞬間収益比」という明確な意味になる。

案B: 平衡ではなく上限を測る
  per-capita gain ではなく
  「単独個体が最良のcellにいるときの理論最大取得速度」を
  決定論計算で出して比較する（シミュレーション不要）。
  chem: chem_uptake × 2.0 × A_eff × H(C_eq, half)
  light: light_uptake_coef × 2.0 × A_eff × H(I_peak, half) と I_peak の小さい方
  これは「burst」という言葉の定義に最も忠実で、
  人口動態のfeedbackが一切混入しない。

案C: 両方出す
  案Bを選定gateに、案Aを診断に使う。
```

**案Bを選定gateにすることを推奨する。** Phase Aの目的は「進化結果からパラメータを選ばないこと」
（Exp13 §4 冒頭）であり、人口平衡に依存する量を選定に使うのはその目的と矛盾する。

なお `BURST_RATIO >= 2.0` / `>= 1.5` という閾値自体は、
窓と定義を揃えた後で改めて到達可能性を検算すべきである
（前回レビューで指摘した「閾値と実行条件の整合を事前に検算する」一般則）。

# 9. V1.9以降のメインストリームストーリー

## 9-1. O-1: `light_absorption = 0` からの立ち上がりは動くが極端に遅い

### 機構は成立する（確認済み）

`evosim/genome.py` の `mutate()` は

```python
child = parent * np.exp(rng.normal(0.0, sigma, N_GENES))
child += rng.normal(0.0, additive_frac * sigma * GENE_SCALE)
```

で、加算項があるので `parent=0` からでも正値が出る。
また `simulation.py` の `ABILITY_EPS = 1e-6` は、生成される値より十分小さい。

```text
additive σ = additive_frac(0.01) × mutation_rate(0.05) × GENE_SCALE[light_abs](0.5)
           = 2.5e-4
典型的な初回変異値 ≈ 2e-4  >>  ABILITY_EPS = 1e-6
```

**したがってストーリー §3.3 の主張「現行遺伝機構だけで経路を作れる」は正しい。**

### さらに良い性質: adaptive valley が無い

`light_absorption = a` に対して:

```text
利益 = light_uptake_coef(2.0) × a × A_eff × phi × H     (供給律速でない場合)
費用 = organ_upkeep(0.05) × matter × a
```

どちらも `a` に比例するので、**比は `a` に依存しない。**
`M=1`, `A_eff=1`, `H≈0.5` なら利益/費用 ≈ 20 で、
**最初の微小変異の時点から正の選択がかかる。** 越えるべき谷が存在しない。
これはV1.9にとって非常に good news であり、ストーリーに明記する価値がある。

### 懸念: 立ち上がりの時間スケール

問題は選択の**強さ**である。`a = 2e-4` のときの純利益は

```text
2.0 × 2e-4 × 1 × 0.5 - 0.05 × 1 × 2e-4 ≈ 1.9e-4 E/tick
```

で、維持費 0.52 E/tick に対して **約0.04%** である。完全にdrift支配であり、
目標水準 0.3 まで到達するには乗算変異の対数ランダムウォークが必要になる。

### 変更提案（OPTIONAL）

Exp14を事前登録する前に、次を決定論または軽量シミュレーションで見積もることを提案する。

```text
- a=0 から a=0.01（Energy取得が maintenance の1%相当）へ到達するまでの
  期待世代数（中立近似 + 弱選択）
- Exp14 の tick 予算がその何倍か
- 到達しない場合、
  (a) GENE_SCALE[light_absorption] を上げる
  (b) additive_mutation_frac を上げる
  (c) 初期値を 0 ではなく 0.01 程度にする
  のどれを選ぶか、結果を見る前に決めておく
```

これはExp11で「stationarity閾値とtick予算の整合を事前検算しなかった」失敗と
**同じ型の失敗を防ぐ**ものである。

## 9-2. O-2: endosymbiosis E2以降はdata-model変更である

ストーリー §6 の E1→E4 の段階分けは、生物学的には正確で順序も妥当である

# 12. 付録 — 検算スクリプト

本書 §3-1 / §4-1 / §4-2 / §4-3 / §3-2 の数値を再現するもの。
現行 `evosim/physiology.py` の `maintenance_and_movement` と

```python
import math

# INITIAL_GENOME (Exp13 Phase A/B は全14遺伝子固定 -> body_size=1.0)
SENS, MEM, DR, POWER, EFF = 0.4, 0.5, 0.5, 0.5, 1.0
# light specialist: light_abs=2.0, chem=0.3, nutrient=0.5, predation=0.05, corpse=0.2
ORGAN_LIGHTSPEC = 2.0 + 0.3 + 0.5 + 0.05 + 0.2
BMR_COEF, BMR_CORE = 0.3, 0.15          # V1.7 選定値

def maint(M, organ_sum=ORGAN_LIGHTSPEC, core=BMR_CORE):
    bmr   = core + (BMR_COEF - core) * M ** 0.75
    organ = 0.05 * M * organ_sum
    sense = 0.02 * SENS ** 2
    memb  = 0.03 * MEM * M ** 0.5
    res   = 0.02 * DR * M
    v     = 0.6 * 3.0 * POWER / math.sqrt(M)      # wander速度 (phi=1)
    move  = 0.05 * M * v * v / EFF                # move_cost * M * v^2 / eff
    return bmr + organ + sense + memb + res + move

# (1) 夜を越せるか: E_max = 100*M
for M in [0.20, 0.246, 0.30, 0.33, 0.50, 0.80, 1.00]:
    print(M, round(maint(M), 4), round(100 * M / maint(M), 1))

# (2) half-sine cycle の period平均 factor
mean_factor = 0.5 * (2 / math.pi)        # day_fraction=0.5
print("mean daylight factor =", round(mean_factor, 5))          # 0.31831
print("energy中立な light_max =", round(1.2 / mean_factor, 3))   # 3.770

# (3) rescue ladder
for lm in [1.2, 1.5, 1.8, 2.4, 3.77]:
    print(lm, round(lm * mean_factor, 4), "vs", round(maint(1.0), 4))

# (5) H(C, 6.15)
for C in [12.3, 1.52, 0.5, 0.02]:
    print(C, round(C / (C + 6.15), 4))
```
