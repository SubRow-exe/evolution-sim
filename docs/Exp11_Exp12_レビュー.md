# 1. Exp11の正式判定をどう読むべきか

## 1-1. `CONTROL_NOT_REPRODUCED` は紙一重の判定である

対照妥当性条件は `p_low >= 0.50` を8 seed中5 seed以上、である。

ここで `p_low = fraction(body_size <= 0.21)` なので（`tools/exp11_common.py`）、

```text
p_low >= 0.50   ⟺   median body_size <= 0.21
```

が厳密に成り立つ。**この条件は「集団の中央値が下限0.2の5%以内にある」と等価**である。

実測（`docs/Exp11_結果考察.md` §4.1）では `bmr_core=0` のB1で

```text
body_size median (8 seedの中央値) = 0.2164   → 下限0.2の +8.2%
```

だった。**下限の5%以内という要求に対し、実測は8.2%。3ポイント差で外している。**

初期値1.0から0.2164（4.6倍の縮小、下限まであと8%）まで落ちている集団を
「小型化が再現しなかった」と記録するのは、事前登録手続きとしては正しいが、
**現象の記述としては明確に誤解を招く**。

`Exp11_考察.md` §10 は「小型化方向の圧力自体は見えているが…判定できるほど進行しなかった」と
書いており方向は正しいが、**なぜ空振りしたかの機構（閾値が中央値条件と等価で、
それが下限の5%に置かれていた）を書いていない**。ここは明記すべきである。

### seed8を外れ値として明示すべき

per-seed `p_low` は

```text
seed1-7: 0.440 0.441 0.458 0.342 0.237 0.267 0.427
seed8  : 0.011
```

で、**seed8だけが桁違いに外れている**（`bmr_core=0` の body_size mean range 上端 0.3054 は
seed8と考えられる）。

7 seedは「中央値が0.21をわずかに上回る」帯に集まっており、seed8だけが別の状態にある。

これは単なるばらつきではなく、**同一 `bmr_core=0` 条件で初期条件依存の分岐が起きている可能性**を
示す。Exp12はCase D（`MULTISTABLE_OR_UNRESOLVED`）を用意しており、
かつ同じseed 1-8を使うので、**seed8を事前登録された注視対象として明記する**ことを推奨する。

## 1-2. 全候補 0/8 Green の真因は `p_low` ではなく `late_drift` である

`Exp11_結果考察.md` §3.2 は全15候補が `0/8 → B1_FAIL` とだけ記録しており、
**どの条件で落ちたかを書いていない。** これは結果記録として不十分である。

per-seed Green条件（`docs/Exp11_実験計画案.md` §11.2）は6つあるが、実測から機械的に特定できる。

| bmr_core | p_low median [range] | p_high | late_drift median [range] | 落ちた条件 |
|---:|---|---:|---|---|
| 0.100 | 0.0048 [0, 0.0566] | 0 | 0.3055 [0.2588, 0.4021] | **条件5のみ**（全8 seedが>0.10） |
| 0.150 | 0.0000 [0, 0.0075] | 0 | 0.2374 [0.1966, 0.3077] | **条件5のみ**（全8 seedが>0.10） |
| 0.200 | 0.0000 [0, 0.0209] | 0 | 0.2438 [0.1695, 0.3307] | **条件5のみ**（全8 seedが>0.10） |
| 0.300 | 0.0000 [0, 0] | 0 | 0.1264 [0.0978, 0.2127] | **条件5**（最小0.0978で最大1 seedしか通らず、7/8に届かない） |

つまり **`bmr_core >= 0.100` では条件2（`p_low<0.25`）も条件3（`p_high<0.25`）も全seedで通っており、
落としたのは条件5（`late_drift <= 0.10`）だけである。**

これは判定の意味をまるごと変える。

- 「候補が小型化を抑えられなかった」のではない
- 「候補は小型化を抑えたが、10,000 tick時点でまだ動いていたので stationarity 条件で落ちた」

`Exp11_考察.md` §2 は「事前登録判定が失敗した理由は…下限へ張り付かなかったため」と
`CONTROL_NOT_REPRODUCED` だけを理由に挙げているが、**仮に対照が通っていても、
条件5によって全候補が `B1_FAIL` になり `TRANSITION_ELIGIBLE` は空のままだった。**
結論は同じ `NO_SELECTION / REVIEW` だが、**理由が2つあり、より本質的なのは条件5のほうである。**

→ `Exp11_結果考察.md` §3.2 に「候補ごとにどの条件で落ちたか」の列を追加し、
`Exp11_考察.md` §2 の因果記述を修正することを推奨する。

## 1-3. 根本原因は「stationarity要求とtick予算の整合性を誰も検算しなかった」こと

条件5そのものは壊れていない。同じ指標でB2（chem-only）は

```text
late_drift median 0.0090 〜 0.0618（全15水準）
```

と**すべて0.10を大きく下回っている**（`Exp11_結果考察.md` §4.2）。
指標は小さい値をきちんと返す。**B1が10,000 tickで本当に定常でなかった**のである。

したがって問題はこうなる。

> Exp11は「10,000 tick」と「late_drift ≤ 0.10」を独立に決め、
> **この2つが両立しうるかを事前に一度も検算しなかった。**

これは前回レビューの帰結でもある。私は 2-5 で「stationarity をGreenの必須条件へ」と提案し、
`docs/V1.7_Exp11_レビュー判断.md` 2-5 でそれが採用され、`late_drift <= 0.10` として実装された。
**提案の方向は妥当だったが、「その閾値が与えられたtick予算で達成可能か」を検算しなかったのは
私のレビューの欠落である。** 同様に 2-2 の対照妥当性条件も、私は概念だけを示し
閾値の操作化（`p_low>=0.50` が中央値条件と等価であること）を検討しなかった。

**Exp12で同じ失敗を繰り返さないための一般則を、判定ルールへ明文化することを推奨する。**

```text
判定閾値を事前登録するときは、その閾値が
「実行予定の条件（tick数・seed数・観測窓）で到達可能か」を
既存データまたはパイロットで必ず先に検算する。
```

# 3. Exp12 実験計画案のレビュー

## 3-1. ★最重要: 判定ルールに構造的な穴がある（依頼事項12への回答）

**「減速しながら低下する軌跡」が `AMBIGUOUS` に落ちる。そしてそれこそが、
平衡変更仮説が正しいときに観測されるはずの軌跡である。**

§13の分類を整理する。

```text
STATIONARY_LIKE   : |drift_23| <= 0.05 かつ |drift_34| <= 0.05 かつ |slope| <= 0.05
PERSISTENT_DECLINE: drift_23 < -0.05 かつ drift_34 < -0.05 かつ slope < -0.05
AMBIGUOUS         : それ以外
```

新しい平衡へ指数的に漸近する軌跡を考える。ブロック間の変化率は幾何級数的に減衰するので、
例えば

```text
drift_12 = -0.15,  drift_23 = -0.07,  drift_34 = -0.03
```

という並びになる。これは

- `|drift_23| = 0.07 > 0.05` → **STATIONARY_LIKE ではない**
- `drift_34 = -0.03 > -0.05` → **PERSISTENT_DECLINE でもない**
- → **AMBIGUOUS**

**平衡へ収束しつつある run が、まさにその理由で分類不能になる。**

§14 は `STATIONARY_LIKE >= 6/8` か `PERSISTENT_DECLINE >= 6/8` しか受け付けないので、
このパターンが多数を占めれば全条件が `UNRESOLVED` になり、
§15 には「大半が UNRESOLVED」に対応する Case が無い（Case Dはseed間分岐の話）。
**56 run × 50,000 tick を投じてverdictが出ない。**

しかもExp11の実測はこのパターンを予告している。`bmr_core=0.300` の late_drift は
2,000 tick窓で 0.1264 まで下がっており、**減速はすでに始まっている**。

### 推奨する修正: 「減速」を一級の分類として持つ

平衡と遅延を分けるのは「変化が止まったか」ではなく **「変化率が縮んでいるか」** である。
50,000 tickという有限窓で前者を要求するのは、そもそも識別問題として不適切である。

最小の追加で済む案を2つ挙げる。どちらか、または両方。

**案A: 減速比テスト（実装がほぼゼロ）**

```text
DECELERATING_DECLINE:
    drift_23 < 0 かつ drift_34 < 0
    かつ |drift_34| / |drift_23| <= 0.6

PERSISTENT_DECLINE (改):
    drift_23 < -0.05 かつ drift_34 < -0.05
    かつ |drift_34| / |drift_23| > 0.8     # 減衰していない
```

`DECELERATING_DECLINE` は平衡変更側の証拠として `STATIONARY_LIKE` と合算する
（§14.1を `STATIONARY_LIKE + DECELERATING_DECLINE >= 6/8` にする）。

**案B: 漸近値の推定（情報量が最も多い）**

各runの tick 10,000–50,000 の median body_size 系列へ

```text
b(t) = b_inf + A * exp(-t / tau)
```

を当てはめ、**`b_inf`（推定平衡body_size）と `tau`（緩和時定数）を報告する**。

- `b_inf` が下限0.2から有意に離れていれば → 平衡変更仮説を支持
- `b_inf` が0.2近傍へ収束すれば → 遅延仮説を支持
- `tau` が観測窓50,000 tickと同オーダー以上なら → **観測窓が足りないことが定量的に言える**

これはQ3（収束位置は `bmr_core` に応じて系統的に変わるか）に**直接**答える唯一の方法でもある。
現行案はfinal値と傾きしか見ないので、「まだ動いている run 同士の収束先の順序」を比べられない。
`tau` を出せば §15 Case C（`GENERATION_LIMITED`）の判断にも根拠が付く。

§11.4 に「後半線形傾き」があるが、**線形回帰は減速を検出できない**（減速する系列に直線を当てると
単に平均傾きが出るだけ）。線形モデルは診断として残しつつ、主判定は上記へ移すべきである。

## 3-2. ★`max_population_halt = 10,000` と 50,000 tick の相互作用（依頼事項11への回答）

§9 は Exp11 の `max_population_halt = 10,000` をそのまま引き継いでいる。
だが run長は5倍になっている。**同じ上限を保つことは中立な選択ではない。**

Exp11 B1 `bmr_core=0` の10,000 tick時点の実測:

```text
final population   5658  [4224, 5866]
biomass_fraction   0.4658
→ 導出: 体内Matter = 0.4658 × 3280 ≒ 1528、個体あたり平均matter ≒ 0.270
```

body_size がさらに下限へ寄れば個体あたりmatterは0.24前後まで下がりうる。
その場合、同じ体内Matterでも個体数は約6,400、biomass_fraction が0.7台まで伸びれば
**10,000到達は十分ありうる範囲**にある。

そして §10 は POP_HALT run について「その後の未観測windowのstationarity判定はN/A」と定めている。
つまり:

> `bmr_core=0`（Q1に答えるための対照）が途中でPOP_HALTすると、
> **drift_23 / drift_34 が計算できず、その seed は `STATIONARY_LIKE` にも
> `PERSISTENT_DECLINE` にも数えられない。**
> §14 は8 seed中6以上を要求するので、3 seed halt した時点でどちらの判定も到達不能になる。

**POP_HALTが事実上の「判定不能」として静かに効く。** これは §1-3 と同じ種類の噛み合わせ不良である。

### 推奨

1. **`max_population_halt` を引き上げる**（例: 20,000＝現行Config default）。
   Exp11 §8 自身が「これはpopulationを抑制する生態ルールではなく計算安全装置」と定義している。
   run長を5倍にしたなら安全装置の位置も見直すのが筋である。
   ただし計算コストは個体数に比例するので、上げる分の時間見積もりが必要（§3-8）。
2. 引き上げない場合は、**POP_HALT runを判定でどう扱うかを事前登録する。**
   最低限「POP_HALT到達tickまでのblockでdriftを計算し、到達したblockまでを使う」と決めておく。
3. どちらにせよ、**Exp11 B1の population 時系列（stats.csv）から50,000 tickでの到達可能性を
   事前に外挿して記載すること。** 生データはまだartifactにある。

## 3-3. 主判定の統計量を mean から median / log へ移すべき

§11.2 の block平均 `B1..B4` は **mean body_size** で定義され、§13 の主判定はこれを使う。

body_size分布は

- 下限0.2でクリップされる
- 変異が乗算的（対数正規、`evosim/genome.py`）

ため、**下限近傍では強く右に裾を引く**。実測でもB1 `bmr_core=0` は mean 0.2278 / median 0.2164 で、
mean が median を5%上回っている。少数の大型個体が mean を動かすので、
**mean はブロック間で median よりずっと大きく揺れる。**

Exp11の late_drift（mean基準）が0.20〜0.48という広いseed間レンジを示したのは、
実体の非定常性に加えて**この裾の効き**も乗っている可能性が高い。

### 推奨

- §11.2 / §13 の主判定を **median** ベースへ。mean は併記する
  （§11.1 は「meanとmedianの両方を使う」と書いてあるが、§11.2以降の判定式は mean だけになっている。不整合）
- さらに堅牢にするなら **`log(body_size)` の平均**を使う。変異が乗算的なので対数が自然なスケールであり、
  「下限からの距離」も `log(b / 0.2)` という素直な量になる
- `drift` の分母 `max(0.2, |B_k|)` は body_size が0.2近傍のとき分母が実質固定されるため、
  対数差 `log(B_k) - log(B_{k-1})` に置き換えるほうが解釈が単純

## 3-4. B2 を安く足せる（依頼事項9への回答）

**§5.1 の「B2/B3をExp12から外す」判断には、部分的に反対する。B2は入れるべきである。**

理由は情報効率ではなくコストである。シミュレーション時間は概ね個体数に比例する。

```text
Exp11実測 final population 中央値
  B1 (bmr_core=0): 5658
  B2 (bmr_core=0):   90     ← 約60分の1
```

**B2の50,000 tick runは、B1の50,000 tick runのおよそ数十分の1のコストで走る。**
7水準 × 8 seed のB2を丸ごと足しても、B1アームの数%程度にしかならない。

そして B2 は科学的に極めて有用である。

- Exp11時点で **B2の late_drift は全水準 0.009〜0.062 と定常条件を大きく下回っている**
  → **stationarity指標が正しく「定常」を返すことを示す陽性対照**になる。
  Exp12の主判定は「変化が止まったか」を測る指標に全面的に依存しているので、
  その指標が機能することを同一実験内で示せるのは大きい
- B2 の body_size は 0.77 → 1.11 と `bmr_core` に対し（細かな上下はあるが）全体として上昇している。
  B1が下限近傍で潰れているのに対し、**B2は内部領域にいる**。
  「内部平衡が存在しうるか」という問いに、B1より直接的に答える条件である
- Case D（多安定）の判断にも、環境が2つあるほうが強い

§5.1 の理由2「計算時間が大きく増える」は、上の数値に照らすと**B2については成り立たない**。
B3（final pop 5544、B1と同規模）を外す判断は妥当なので、**B3のみ除外、B2は追加**を推奨する。

## 3-5. `final body_size median > 0.23` sentinel の出所を明記すべき

§14.1 の 0.23 は、Exp11実測の `bmr_core=0.030 → 0.2334` の**すぐ隣**にある。
実測の分布の中に閾値を置くのは、事後調整に見える形である（実際には違うとしても）。

0.23 = **下限0.2 × 1.15** なので、そう書けば原理的な導出になる。

→ 「`GENE_MIN(body_size) × 1.15`」と定義を書くこと。
あるいは実測クラウドから離すために `× 1.25 = 0.25` にする。どちらでもよいが、
**数値をそのまま置かず導出を書く**ことが重要である。

## 3-6. 代表値・seed数（依頼事項1・2・5・8への回答）

| 依頼 | 回答 |
|---|---|
| 1. 50,000 tick / 7水準 / 8 seedは過不足ないか | **tick数は「事前に検算していない」のが問題**であって多寡ではない。§1-3の一般則に従い、Exp11 B1のsnapshot系列から `tau` を先に推定し、50,000 tickが `tau` の何倍かを示してから確定すべき。`tau` が 20,000 tick程度なら50,000で足りるが、`tau` が 50,000 tickオーダーなら足りない。**この検算はExp11の既存生データだけでできる**（追加run不要） |
| 2. 代表値の選び方にバイアスがないか | 大きなバイアスは無い。ただし `0.000` と `0.030` は Exp11 で median 0.2164 / 0.2334 とほぼ同じ状態にあり、**主問い（平衡か遅延か）に対しては冗長**。計算枠が苦しければ `0.030 → 0.200` の入れ替えが、最大のギャップ（0.150–0.300）を埋める点で情報量が高い。枠に余裕があるなら現状のままでよい |

| 8. 0.200を足すべきか | **主問いのためには不要。**「収束位置が `bmr_core` とともに系統的に増える」（Case A）の検証には、0.150 と 0.300 の2点で単調性は見える。足すなら §3-4 のB2追加のほうが優先度が高い |

## 3-7. 世代診断（依頼事項6への回答）

**`max_generation` 単独は明確に弱い。generation median / Q90 を必須にすべきである。**

- `max_generation` は集団全体の**極値統計**である。B1では個体数が3,000〜5,600あるので、
  実質「最速で回った1系統の世代数」になり、集団の代表的な世代時間とは乖離する
- `Exp11_考察.md` §9 自身が「max_generationは極端値になり得る」と書いており、認識は共有されている
- **コストはゼロである。** snapshot CSVは既に個体ごとの `generation` 列を持っている
  （`evosim/recorder.py` の snapshot ヘッダ: `id, parent_id, lineage_id, generation, age, ...`）。
  summarizer側で分位を取るだけで、再実行も追加記録も要らない

→ §11.5 / §12 の「可能なら」「実装コストが小さい場合は」という条件付き記述を外し、
**generation の median / Q90 を必須指標にする**ことを推奨する。

Case C（`GENERATION_LIMITED`）は世代数を根拠に発動する判定なので、
その根拠指標が極値統計のままでは判定が成立しない。

## 3-8. 計算量と Actions の6時間上限（依頼事項7・11への回答）

§19 が「timeout値を推測で固定しない」としているのは正しい。ただし**timeout設定では
解決できない上限がある**ことを計画に書くべきである。

```text
GitHub Actions の hosted runner は 1 job あたり 6時間が上限。
exp10.yml / exp11.yml は timeout-minutes: 350（= 上限直下）を使っている。
```

**1 run = 1 job = 50,000 tick を高population下で回すので、6時間を超えたら
timeout値を何に設定しても救えない。**

粗い見積り（Exp10 exploratoryの「約40分 / 10,000 tick / 約6,500個体」を基準に導出）:

```text
Exp11 B1 bmr_core=0 は10,000 tickで約5,600個体 → 同オーダー
population がその水準で推移するなら 50,000 tick ≒ 3時間
population が増加を続けるなら 4〜6時間、または上限超過
```

**つまり「たぶん入るが余裕は無く、最も重い bmr_core=0（= 対照）が最初に溢れる」。**

→ 推奨:

1. **Exp11の `performance.csv` から実測 tick/sec を bmr_core別に出す**（追加run不要、artifact消滅前に）
2. その上で、6時間に収まらない見込みなら **checkpoint / resume か、
   25,000 tick × 2段の分割**を実装要件に入れる。50,000を1本で走らせる §8.1 の方針は、
   6時間上限と両立しない可能性がある
3. §3-2 で `max_population_halt` を上げる場合、時間見積りも上げる

「50kでなお遅い場合の停止/延長基準を事前登録すべきか」（依頼7）への回答は **すべきである**。
§3-1 案Bの `tau` があれば、「`tau` > 観測窓/3 なら `WINDOW_INSUFFICIENT` として延長を検討」
という形で客観的に書ける。

## 3-9. Exp11 same-seed 再現性を正式gateにすべき（依頼事項10への回答）

**すべきである。しかも `bitwise` で要求できる。**

確認したところ、**`evosim/` はExp11実行時のSHA `8da7311` から現在の `main` まで一切変更されていない**
（`git diff 8da7311 origin/main -- evosim/` が空）。修正はすべてcollect側・workflow側である。

`ticks` はループの終了条件でしかなくRNG消費に影響しないので、
**Exp12 の tick 10,000 時点のsnapshotは、Exp11 same-seed の最終snapshotと bitwise 一致するはず**である。

これは非常に強く、かつタダな integrity gate である。

→ §17 の「完全bitwise一致を要求するか…実装時に合わせる」を、
**「tick 10,000 snapshot の bitwise 一致を必須gateとする。不一致なら正式解釈を停止」**へ確定することを推奨する。
Exp11で起きたcollect側の読み違いは、このgateがあれば即座に露見していた。

## 3-10. 長期runのMatter枯渇監査（依頼事項11への回答・続き）

`bmr_core=0` の biomass_fraction は10,000 tickで既に 0.4658 で、**上昇途中**である。

50,000 tickで free nutrient が枯渇に近づくと、

> body_size が「止まった」のは選択平衡ではなく、
> **系のMatterを使い切って新規個体を作れなくなったから**

という状態が起こりうる。この状態を `STATIONARY_LIKE` と分類したら、Exp12の結論は無効になる。

§11.6 は free nutrient / biomass_fraction を記録するが「主判定には使わない」としている。
**これは診断ではなく除外条件にすべきである。**

→ 推奨:

```text
MATTER_LIMITED:
    後半blockで free nutrient total が総Matterの X% 未満
    → その run の stationarity 判定を別枠にし、
      平衡変更の証拠として数えない
```

X の値は、Exp11 B1の10,000 tick時点の free nutrient 実測から事前に決められる。
